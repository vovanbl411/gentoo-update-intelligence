# Design

## Context

Существующий Provider читает cache из закреплённого Git commit; resolver выбирает точный ebuild по first-parent истории, генератор пока рассчитан на Gentoo без настройки masters. HTTP POST синхронен. Активный `add-local-compose` предусматривает внешний готовый snapshot: этот change заменяет его предпосылку после согласования и интеграции, не предполагая завершения того change.

## Goals / Non-Goals

**Goals:** воспроизводимые ревизии, изоляция ошибок пакетов, ограничение нагрузки и видимый прогресс.

**Non-Goals:** выполнение обновлений системы, произвольные URL репозиториев из пользовательского плана, гарантия доступности всей истории или всех оверлеев.

## Decisions

### Публикация снимков
Gentoo runtime синхронизирует Git-репозиторий в постоянный volume сразу и каждые пять часов. Fetch происходит отдельно от опубликованной ссылки; только успешная проверка полного commit атомарно переключает ссылку. Анализ закрепляет commit и объекты сохраняются до окончания использующих их работ. При первом сбое готовность подготовки недоступна, при последующих сохраняется предыдущая ссылка. Альтернатива — изменяемый checkout: он допускает смешение ревизий.

### Репозитории и metadata
План разбирается существующим Parser; имена репозиториев разрешаются через контролируемый каталог известных URL и masters, а не через произвольный сетевой адрес из ввода. Оверлей загружается один раз по требованию; для каждого анализа фиксируются его commit и commits masters. Неоднозначное или отсутствующее имя не угадывается: запись получает причину. Готовый cache проверяется по точной версии и закреплённому источнику; иначе resolver ищет ebuild, а генератор расширяется для конфигурации закреплённых masters и изолированного checkout. Сохранённый результат ключуется точной версией, source/blob, commits masters, профилем и версией генератора/Portage. Это предотвращает неверное повторное использование. Альтернатива — всегда генерировать: она медленнее и игнорирует готовый cache.

Совпадающие запросы объединяются по полному ключу; ограниченный пул генерации действует на весь сервис, а не на отдельный запрос. Ошибки фиксируются на стороне before/after конкретной записи; успехи передаются в существующий отчёт. Исходная версия может быть не определена планом: в этом случае показывается причина, а не придуманная версия.

### Асинхронный API
POST валидирует план и сохраняет задание до ответа `202` с UUID; GET по UUID возвращает статус `pending`, `running`, `completed` или `failed`, прогресс и при завершении результат. Прогресс считает завершённые уникальные единицы подготовки и их общее число после разбора; до определения общего числа отображается стадия. Повторный GET не запускает работу. Существующие сохранённые результаты читаются как `completed`. При рестарте незавершённые задания возобновляются с закреплёнными ревизиями либо завершаются с явной причиной при невозможности восстановления. Повтор POST автоматически не выполняется. Альтернатива — удерживать POST открытым: длительная синхронизация не позволяет надёжно показывать прогресс и переживать разрыв связи.

## Risks / Trade-offs

- Большая история и оверлеи занимают место → сохранять нужные Git-объекты, документировать размер и не удалять закреплённые объекты во время работ.
- Недоступные masters или неполная история → явная причина на пакете, остальные результаты сохраняются.
- Генерация исполняет ebuild-код → изолированный Gentoo runtime с ограниченными ресурсами, без секретов и доступа к хосту; контролируемые источники и ограниченная сеть.
- Изменение API ломает старые клиенты → обновить API и UI вместе, сохранить чтение старых результатов и документировать миграцию.

## Migration Plan

После согласования объединить с Compose, добавить постоянный volume и миграцию заданий, затем обновить backend и frontend вместе. Проверить чистый запуск и повторное чтение старых анализов. Откатить образы и конфигурацию можно до миграции данных либо после проверки обратной совместимости схемы; volume и сохранённые анализы не удалять.
