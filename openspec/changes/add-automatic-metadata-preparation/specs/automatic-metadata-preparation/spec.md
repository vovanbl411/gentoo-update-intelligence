# Spec Delta

## Purpose

Обеспечить автоматическую подготовку воспроизводимых metadata для анализа пользовательского плана обновления Gentoo.

## ADDED Requirements

### Requirement: Синхронизация дерева
Gentoo-контейнер SHALL автоматически синхронизировать основное дерево при запуске с пустым volume и затем каждые три часа, сохраняя данные в постоянном volume.

#### Scenario: Первый запуск
- **WHEN** сервис запускается с пустым volume и источник доступен
- **THEN** синхронизация создаёт пригодное для анализа состояние без ручной подготовки снимка

#### Scenario: Ошибка очередной синхронизации
- **WHEN** синхронизация после успешной попытки завершается ошибкой
- **THEN** сервис продолжает анализ с последним успешным состоянием и не публикует частичное обновление

#### Scenario: Нет успешного состояния
- **WHEN** первоначальная синхронизация не удалась и успешного состояния нет
- **THEN** сервис сообщает о недоступности подготовки, не выдавая частичное дерево за успешное состояние

### Requirement: Закреплённые репозитории
Каждый анализ SHALL использовать закреплённые полные ревизии всех необходимых репозиториев и сохранять их в provenance результата. Синхронизация SHALL не менять ревизии выполняющегося анализа.

#### Scenario: Обновление во время анализа
- **WHEN** синхронизация публикует новую ревизию во время анализа
- **THEN** все обращения этого анализа используют ранее закреплённые ревизии

### Requirement: Подготовка по плану
Сервис SHALL определять необходимые репозитории и точные версии из плана, загружать известные оверлеи по требованию и переиспользовать уже загруженные репозитории.

#### Scenario: Повторный план
- **WHEN** повторный анализ требует уже доступный оверлей
- **THEN** сервис переиспользует его без повторной полной загрузки

### Requirement: Получение точных metadata
Сервис SHALL использовать готовый cache точной версии, а при его отсутствии применять существующие resolver и генератор, если доступны исходники и необходимые master repositories. Результат SHALL содержать provenance использованных metadata и исходников.

#### Scenario: Готовый cache
- **WHEN** cache точной версии доступен в закреплённой ревизии или совместимом сохранённом результате
- **THEN** сервис использует его без повторной генерации и показывает источник

#### Scenario: Генерация
- **WHEN** cache отсутствует, но точный ebuild и необходимые master repositories доступны
- **THEN** сервис готовит metadata точной версии и сохраняет provenance для повторного использования

### Requirement: Частичный отчёт
Ошибка подготовки отдельного пакета SHALL не прерывать обработку остальных записей. Для каждой записи отчёт SHALL показывать доступный diff с источниками либо конкретную причину отсутствия сравнения.

#### Scenario: Недоступные данные
- **WHEN** оверлей неизвестен, история недоступна, master repository отсутствует или генерация завершается ошибкой
- **THEN** соответствующая запись содержит конкретную причину и сторону сравнения, а остальные записи попадают в отчёт

### Requirement: Ограничение работы
Сервис SHALL дедуплицировать совпадающие запросы подготовки и ограничивать параллельную генерацию настраиваемым положительным пределом.

#### Scenario: Большой план
- **WHEN** план из 1000 или более записей содержит повторяющиеся запросы
- **THEN** одинаковая подготовка выполняется один раз для совместимого набора входов, а число одновременных генераций не превышает настроенный предел

### Requirement: Состояние анализа
Сервис SHALL предоставлять сохранённый идентификатор и состояние обработки, прогресс и итоговый результат для повторного чтения. Сбой обработки SHALL быть виден с причиной.

#### Scenario: Обработка продолжается
- **WHEN** клиент запрашивает состояние принятого, но не завершённого анализа
- **THEN** ответ содержит состояние и прогресс выполненных и общего числа единиц работы

#### Scenario: Завершение
- **WHEN** обработка завершается
- **THEN** результат доступен по тому же идентификатору и сохраняет отчёт и provenance
