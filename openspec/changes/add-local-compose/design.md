# Design

## Context

Backend получает параметры PostgreSQL и Metadata Provider через переменные окружения; путь к локальному Git repository и полный commit уже входят в его конфигурацию. Metadata Provider читает cache-объекты закреплённого commit. Frontend сейчас запускается через Vite и использует proxy `/api`, тогда как production-раздача собранного UI ещё не определена. См. `proposal.md` и новую спецификацию `local-compose`.

## Goals / Non-Goals

**Goals:**

- Собрать локальный стек, который можно запустить по инструкции из чистого checkout.
- Сохранить существующие HTTP-маршруты frontend и backend при раздаче собранного UI.
- Явно связать экземпляр backend с подготовленным read-only Git-снимком и заданным commit.
- Сохранять записи анализов между пересозданиями контейнеров.

**Non-Goals:**

- Менять HTTP API, формат результата или логику анализа.
- Автоматически загружать/обновлять Gentoo snapshot или генерировать metadata.
- Добавлять Redis, аутентификацию, внешний доступ или production deployment.

## Decisions

### Отдавать собранный frontend из отдельного статического runtime

Собирать frontend в Node build stage и копировать статические файлы в небольшой nginx runtime. Nginx обслуживает UI и историю маршрутов SPA через fallback на `index.html`; `/api/` обрабатывается отдельным proxy location с `proxy_pass` на внутренний backend и завершающим `/`, чтобы снять префикс `/api`. Proxy не должен включать перехват ошибок upstream: статусы и тело ошибок backend должны дойти до браузера как ответы API.

Альтернатива — оставить Vite dev server в Compose. Она проще для локальной разработки, но не проверяет собранный frontend и его production routing, который требуется приёмочным сценарием.

### Собирать backend и frontend из checkout

Добавить многоэтапные Docker builds с контекстом из корня репозитория: Go builder создаёт backend binary; Node builder выполняет lockfile-based install и сборку frontend. В runtime-образ backend помещаются binary, Git CLI, который Metadata Provider вызывает через `exec.Command` для чтения Git-объектов, и системные сертификаты. Frontend runtime содержит только собранные assets и конфигурацию nginx.

Альтернатива — использовать готовые образы приложения. В репозитории нет опубликованных образов, а локальная сборка проверяет состояние текущего checkout и не требует отдельной публикации.

### Оставить backend и PostgreSQL во внутренней сети Compose

Все три сервиса используют сеть Compose. Backend получает `GENTOO_UPDATE_INTELLIGENCE_LISTEN_ADDR=0.0.0.0:8080`, чтобы слушать интерфейс контейнера и принимать соединения frontend по имени сервиса. Только frontend получает `ports` с bind address `127.0.0.1`; backend и PostgreSQL не публикуют host ports. Backend ожидает готовности PostgreSQL по healthcheck перед стартом, поскольку при запуске применяет миграцию и открывает хранилище.

Альтернатива — публиковать порты backend и базы для прямой отладки. Это не требуется для браузерного сценария: браузер обращается к API через frontend, а ненужная публикация расширила бы доступ к сервисам.

### Передавать обязательные параметры запуска через локальный env-файл

Compose требует явных значений для абсолютного host path metadata snapshot, полного commit, имени repository, provenance source URL и пароля PostgreSQL. Добавить `.env.example` с безопасными placeholders и внести рабочий `.env` в `.gitignore`. Путь snapshot монтируется в backend read-only; backend получает существующие `GENTOO_UPDATE_INTELLIGENCE_*` параметры и использует прежний API.

Snapshot должен быть подготовлен до запуска и содержать закреплённый commit вместе с cache-объектами версий из плана проверки. Контейнер не выполняет fetch, checkout или генерацию metadata. `SOURCE_URL` остаётся заявленным provenance и не означает сетевую проверку repository.

Альтернатива — запекать snapshot в backend image. Это увеличило бы образ, связало данные Gentoo с релизом приложения и затруднило замену commit без пересборки.

### Использовать именованный volume PostgreSQL для сохранённых анализов

PostgreSQL хранит данные в явно объявленном именованном volume. `docker compose up --build --force-recreate` пересоздаёт контейнеры, сохраняя данные volume. Инструкция должна использовать этот путь и предупреждать, что удаление volume удаляет сохранённые анализы.

Альтернатива — bind mount каталога данных на хост. Именованный volume проще переносить между пересозданиями контейнеров и не требует выбирать host path или управлять владельцем файлов.

## Risks / Trade-offs

- Неподготовленный snapshot или несовпадающий commit приведёт к недоступности Provider либо неполным Lookup → инструкция задаёт предварительные условия и показывает проверку обоих Lookup для `dev-libs/libei`.
- Удаление именованного volume уничтожит сохранённые анализы → инструкция не использует `down -v` и явно отделяет остановку стека от удаления данных.
- Первичная сборка зависит от доступности базовых Docker images → инструкции перечисляют Docker Engine с Compose plugin и сетевую доступность registry для первой сборки.
- Ошибка конфигурации proxy может вернуть UI вместо ошибки API → отдельный интеграционный сценарий проверяет ошибочный JSON API-ответ через frontend proxy.

## Migration Plan

Это новый локальный путь запуска; существующие способы запуска не мигрируют автоматически.

1. Подготовить локальный Git snapshot и проверить наличие полного commit и нужных cache-объектов.
2. Создать локальный env-файл из примера и задать обязательные значения.
3. Запустить Compose со сборкой образов, затем пройти браузерную проверку и сравнить сохранённый результат с GET API.
4. Пересоздать контейнеры без удаления PostgreSQL volume и открыть тот же UUID напрямую.

Для остановки использовать `docker compose down`, сохраняя именованный volume. Удаление volume не является частью отката; оно удаляет данные анализов.
