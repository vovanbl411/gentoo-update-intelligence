# Итоги холодного анализа

Измерения проведены 6–7 ноября 2026 года на Debian 13.7 amd64 в KVM: 1 vCPU, 2 GiB RAM, диск virtio 40 GiB с `cache=none`, swap выключен. Для каждого плана получены три успешные пары cold → warm. Для плана 2 также выполнена одна контрольная пара без измерительного patch. Матрица содержит 14 успешных прогонов; неуспешный запуск плана 3 и ошибки подготовки сохранены отдельно.

Полная таблица каждого прогона, ресурсов, наблюдателя, хостовых помех и этапов находится в [measurement-tables.md](measurement-tables.md). Сырые журналы, полные ответы API, кэши и данные БД сохранены в `/var/tmp/guit-cold-plan-analysis/evidence/raw/`; host-выборка — в `/var/tmp/guit-cold-plan-analysis/evidence/host.jsonl`. SHA-256 архива гостевых данных: `7ad7cc9b08dea567cda94d79480c8729b77df43696a67925a9d58490628505db`.

Для трёх запросов плана 3 metadata уже была в закреплённом исходном repository; остальные 76 результатов сгенерированы. В плане 2 запись 37 устанавливает пакет в новый slot: оба Lookup штатно пропущены с `BINDING_REJECTED`, а отчёт содержит `OPERATION_UNSUPPORTED`. Для плана 3 подтверждены семь пересборок только с after.

Все 14 успешных ответов содержат ожидаемое число запросов и не имеют ошибок Lookup или OOM. Нормализованные полные ответы совпали внутри каждого плана: совпали findings, порядок, Lookup и provenance. Менялись только UUID и автоматически созданные временные пути; оригиналы JSON не менялись. Первый промежуточный отчёт появился через 1.0–1.1 с. Первый отчёт с готовым metadata-результатом появился через 35–40 с для холодного плана 2, через 29–31 с для плана 3 и примерно через 1–2 с для warm.

## Где проходит время

Больше всего времени заняло создание дерева repository для каждой генерации metadata. Parser, Analyzer и окончательная сборка отчёта заняли доли секунды.

| Этап worker | План 2, с | План 3, с |
| --- | ---: | ---: |
| `worker.checkout.main` | 863 [750–869] | 673 [669–677] |
| `worker.checkout.master` | 69 [58–75] | 58 [58–60] |
| `worker.cleanup` | 201 [174–208] | 146 [146–146] |
| `worker.generator_setup` | 133 [115–154] | 110 [96–111] |
| `worker.egencache` | 65 [55–67] | 63 [63–67] |
| `worker.portage_version` | 42 [35–44] | 29 [29–30] |
| Все `worker.prepare` | 1392 [1195–1414] | 1085 [1077–1093] |

В `prepareMetadata` каждый cache miss создаёт временное дерево командами `git clone --shared` и `git checkout --detach --force`, а затем удаляет его через `os.RemoveAll`. На холодном плане 2 main checkout выполнялся 80 раз, на плане 3 — 76. Разбор и Analyzer заняли менее 0.01 с; настройка repositories — менее 0.05 с; `partial_build` и сохранение промежуточных записей — около 3 с за прогон. На `egencache` пришлось 4–6% времени подготовки.

Суммарные интервалы `backend.lookup` составили 2768 с для плана 2 и 2156 с для плана 3 — больше wall time из-за перекрытия Lookup и ожидания единственного preparation slot. Их нельзя складывать с `worker.prepare` или трактовать как время одного анализа. `worker.preparation_slot_wait` также суммирует ожидания отдельных запросов, которые перекрываются между собой.

Warm-прогон проходил за 36–48 с для плана 2 и 36–37 с для плана 3. Worker отметил 80/76 generated-cache hits и ноль генераций. Это подтверждает пользу готового generated-cache; чтение cache внутри worker занимало около 0.02–0.03 с суммарно на холодном плане.

Контейнер worker потребил около 98–99% измеренного user+system CPU всех контейнеров. На госте оставалось не менее 28.6 GiB свободного места; OOM и swap не было. `vda` был занят около 13–14% времени, средняя задержка записи составила 3–4 мс, guest iowait — 63–76 с за холодный прогон. Большая запись совпала по времени с повторными checkout и cleanup; насыщения виртуального устройства на этом стенде не наблюдалось. Cgroup-запись worker составила около 37 GiB для плана 2 и 35 GiB для плана 3. Эти значения показывают суммарный поток записи за прогон; занятое место измерялось отдельно.

Хост наблюдался отдельно. Во время измерений менялись `load1` и swap I/O; максимальный `load1` составлял 5–14. Успешные прогоны имели секундную телеметрию без разрывов больше 1.02 с. Наблюдатель использовал около 1.8–3.6 CPU-секунды, до 14 MiB RSS и 17–22 MiB дисковой записи за холодный прогон. Логический `wchar` процессов — нижняя граница: секундный опрос может пропустить короткоживущие процессы. Cgroup I/O и запись `vda` приведены отдельно.

## Контроль инструментации и исключённый запуск

Единственная контрольная пара плана 2 без patch заняла 1112 с cold и 36 с warm при тех же закреплённых входах. Холодный контроль оказался на 20% быстрее медианы трёх инструментированных прогонов и на 7% быстрее их минимума. Warm-контроль оказался у нижней границы инструментированного диапазона. Одного контрольного запуска при меняющейся нагрузке хоста и фиксированном порядке прогонов не хватает, чтобы доказать отсутствие overhead инструментации или отделить его от фоновых колебаний.

Первый `plan3-pair2-instrumented-cold` завершился timeout в runner. Хост приостановил VM: максимальный разрыв между секундными наблюдениями составил 34 897 с. Поздний полный ответ API показал `completed` 79/79, но содержал две ошибки `METADATA_LOOKUP_FAILED`; он проверку не прошёл и не учитывается. Сырые данные сохранены отдельно. Повтор выполнен как новая пара с пустым cache и БД: cold 1086 с, warm 37 с, без ошибок.

## Следующий эксперимент

Рекомендуемый следующий шаг — проверить повторное использование подготовленных checkout по pinned revision. В ответах API найдены 13 уникальных сочетаний repository и `selected_commit` для плана 2 и 10 для плана 3. Добавление master revisions, profile и Portage runtime не изменило число ключей. При этом main checkout выполнялся 80 и 76 раз.

Текущие затраты на main checkout и cleanup составили 1064 с для плана 2 и 819 с для плана 3. Если время этих этапов примерно пропорционально числу уникальных деревьев, повторное использование 13/10 деревьев вместо 80/76 даёт верхнюю расчётную экономию около 15 и 12 минут cold соответственно. Эта оценка не обещает результата: реальный выигрыш зависит от стоимости подготовки каждого revision и обслуживания кэша.

Эксперименту нужна ограниченная checkout pool с ключом, включающим repository, source commit, masters, profile, generator и Portage version. `egencache` записывает md5-cache в checkout; generation temp directory должен остаться отдельным для запроса. Нужны ограничение размера и очистка pool, защита от одновременной записи в одно дерево и проверки отсутствия переноса metadata между profile/runtime. До включения в приложение сравнить полные результаты с текущей реализацией, проверить provenance и порядок, cache isolation, concurrent requests и eviction. Текущие API, форматы и штатная конфигурация в этой задаче не менялись.

Ограничения переноса: generated-cache был пустым перед cold, но filesystem cache ОС не сбрасывался. Виртуальный диск локальной KVM не воспроизводит производительность произвольного VPS. Ресурсы хоста и один контрольный прогон ограничивают точность сравнения; оценка времени не является SLA.
