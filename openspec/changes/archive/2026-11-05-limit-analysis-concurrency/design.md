# Design

## Context

Задания уже хранятся в PostgreSQL, но HTTP handler немедленно запускает каждое в goroutine. Мотивация описана в proposal.md.

## Goals / Non-Goals

Ограничить всю обработку анализа до Parser и Git. Сохранить `202`, UUID, прогресс и восстановление ревизий. Лимит относится к одному backend. Несколько backend, отмена заданий, rate limiting и изменение лимита worker в scope не входят.

## Decisions

- PostgreSQL хранит очередь. Атомарный UPDATE выбирает самое старое `pending` по `created_at, id` и переводит его в `running/preparing`. Отдельный broker или очередь полных планов в памяти не нужны.
- Один диспетчер забирает задания только при свободном месте. Он просыпается после POST, Resume и завершения анализа, объединяет уведомления и завершается при пустой очереди или заполнении слотов. Ошибка чтения очереди повторяется с задержкой одним диспетчером; уже принятые задания не теряются.
- Активные goroutine учитываются до сохранения конечного состояния. Некорректный сохранённый запрос получает `failed` и освобождает место.
- При запуске единственного backend `running` возвращаются в `pending/queued` без удаления revisions. Resume запускает общий диспетчер, поэтому восстановление также подчиняется лимиту.
- Пустая настройка означает `1`, `0` отключает предел, отрицательное, нечисловое значение и переполнение мешают запуску. Лимит проверяется до подключения PostgreSQL.

## Risks / Trade-offs

- Большой анализ задерживает следующие при лимите `1` → оператор может увеличить предел; строгий порядок завершения при нескольких слотах не гарантируется.
- Очередь может расти на диске, а режим `0` не ограничивает активную работу → это явно описывается в руководстве; admission control не добавляется.
- Возврат running в очередь несовместим с несколькими backend → документируется поддержка одного процесса.
- При недоступности PostgreSQL сохранение состояния удерживает активный слот до восстановления БД, как и прежняя политика повторов.

## Migration Plan

Миграция схемы не требуется. Пересобрать и пересоздать backend; задания и ревизии сохранятся в прежнем volume. Для возврата к прежнему параллелизму установить лимит `0` и пересоздать backend. Рабочие контейнеры в ходе реализации не меняются.
