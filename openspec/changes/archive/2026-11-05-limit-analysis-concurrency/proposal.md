# Proposal

## Why

Каждый принятый план сейчас запускает отдельный анализ без общего предела. Лимит генераций worker не ограничивает разбор планов, Git и временные checkout, поэтому нужен отдельный предел активных анализов.

## What Changes

- По умолчанию backend выполняет один анализ, worker сохраняет предел двух генераций.
- Ожидающие задания остаются в PostgreSQL в состоянии `pending/queued`; слот выделяется до разбора плана и подготовки репозиториев.
- `GENTOO_UPDATE_INTELLIGENCE_ANALYSIS_CONCURRENCY_LIMIT` задаёт неотрицательное целое: `1` по умолчанию, `0` без ограничения, положительное число как предел.
- Прерванные задания возвращаются в очередь с сохранением закреплённых ревизий.
- Документация объясняет независимость лимитов и применение настройки через пересоздание backend.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `automatic-metadata-preparation`: очередь и ограничение активных анализов, восстановление очереди.
- `local-compose`: настройка предела анализов через окружение Compose.

## Impact

Затронуты analysishttp, analysisstore, запуск backend, Compose и документация. Формат API и схема PostgreSQL сохраняются; новые зависимости не нужны. Поддерживается один backend, распределённое выполнение не входит в scope. Приёмка: тесты очереди, режимов `1`, `2`, `0`, восстановления и ошибок, Go checks и строгая проверка OpenSpec. Основной источник новых требований очереди — `automatic-metadata-preparation`; прочие контракты `docs/` не переносятся.
