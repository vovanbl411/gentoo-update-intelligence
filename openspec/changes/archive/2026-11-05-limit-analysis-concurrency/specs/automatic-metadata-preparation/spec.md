## ADDED Requirements

### Requirement: Очередь анализов с настраиваемым пределом
Один backend SHALL ограничивать число активных анализов: по умолчанию `1`, положительное целое задаёт предел, `0` отключает ограничение. Ожидающие задания SHALL храниться в PostgreSQL как `pending/queued` без Parser, Provider и отдельной goroutine на задание. Принятие SHALL сохранять `202` и UUID; выбор SHALL идти по `created_at, id`. Независимый положительный лимит генераций metadata SHALL оставаться `2` по умолчанию.

#### Scenario: Все слоты заняты
- **GIVEN** один анализ выполняется при пределе `1`
- **WHEN** API принимает ещё один план
- **THEN** новый UUID возвращается без ожидания завершения первого анализа, а новое задание остаётся `pending/queued` и не обращается к Provider до освобождения слота

#### Scenario: Несколько слотов или отключённый предел
- **WHEN** предел установлен в `2` или `0` и приняты несколько заданий
- **THEN** одновременно запускается не больше двух анализов при `2`, а при `0` очередь не ограничивает число активных анализов

#### Scenario: Восстановление очереди
- **GIVEN** в базе есть `pending` и прерванные `running`, в том числе с закреплёнными ревизиями
- **WHEN** единственный backend перезапускается
- **THEN** незавершённые задания поступают в общую очередь, обрабатываются в пределах лимита и сохраняют прежние закреплённые ревизии

#### Scenario: Ошибка отдельного задания или очереди
- **WHEN** задание заканчивается ошибкой либо чтение очереди временно недоступно
- **THEN** конечная ошибка задания освобождает слот для следующего, а ошибка чтения повторяется без потери принятых заданий и без запуска второго диспетчера
