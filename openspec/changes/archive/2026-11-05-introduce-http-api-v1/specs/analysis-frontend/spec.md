## ADDED Requirements

### Requirement: Frontend использует DTO v1
Frontend SHALL создавать и читать задания через `/api/v1/analyses` с DTO snake_case и структурированными ошибками. Все состояния, findings, evidence, metadata и причины недоступности SHALL сохранять смысл; страница `/analyses/{id}` и оформление SHALL сохраняться.

#### Scenario: Новый и сохранённый анализ
- **WHEN** пользователь отправляет план или открывает прежний UUID
- **THEN** frontend использует v1, показывает состояние и результат, а запросов к прежнему API не делает

#### Scenario: Неизвестный код ошибки
- **WHEN** API возвращает структурированную ошибку с неизвестным code
- **THEN** frontend показывает её message как текст и сохраняет доступные действия повтора

## MODIFIED Requirements

### Requirement: Отображение результата и неполных данных
Интерфейс SHALL показывать возвращённые статусы и диагностики Parser, записи пакетов
с операциями и доступными версиями, findings с категориями и сообщениями, доступный
metadata diff и его ограничения. `partial` и `unsupported` SHALL отображаться как
результаты анализа; отсутствие данных не означает отсутствие изменений или проблем.

#### Scenario: Результат с metadata diff
- **WHEN** API возвращает записи, findings и доступное сравнение metadata
- **THEN** UI показывает их в исходном порядке, включая доступные изменения EAPI, SLOT/SUBSLOT и IUSE без вычисления собственных правил

#### Scenario: Частичный результат
- **WHEN** Parser имеет статус `partial`
- **THEN** UI явно показывает этот статус, диагностики и доступные записи и findings

#### Scenario: Доступное сравнение без различий
- **WHEN** API возвращает доступное сравнение metadata с compared_fields и без изменений в этих полях
- **THEN** UI сообщает об отсутствии различий в сравнённых полях, не обозначая metadata недоступными и не делая вывода об остальных полях

#### Scenario: Неподдерживаемый ввод
- **WHEN** сохранённый результат имеет статус `unsupported` и пустой список пакетов
- **THEN** UI показывает статус и диагностики без сообщения об успешной проверке безопасности обновления

#### Scenario: Недоступные metadata
- **WHEN** API возвращает недоступный раздел, Lookup status, error, skip_reason или diagnostics/limitations
- **THEN** UI показывает доступную причину и сторону before/after там, где она задана API; если причины нет, сообщает только о недоступности данных

### Requirement: Проверяемые основания findings
Интерфейс SHALL связывать findings с возвращёнными API evidence: пакетами, номерами
строк, токенами, установленными версиями, blockers или индексами контекста, насколько
это позволяет ответ. Finding без entry_index SHALL оставаться видимым. Недоступные
фрагменты исходного плана SHALL не восстанавливаться предположениями.

#### Scenario: Основание изменения USE
- **WHEN** finding содержит ссылки на запись и индексы USE-токенов
- **THEN** UI показывает соответствующие возвращённые токены и доступные номера строк

#### Scenario: Blocker без записи пакета
- **WHEN** finding ссылается на blocker_index и не содержит entry_index
- **THEN** UI показывает finding и связанный blocker, не приписывая его произвольной записи

#### Scenario: Неполная ссылка evidence
- **WHEN** возвращённую ссылку нельзя разрешить по данным результата
- **THEN** UI сохраняет finding и доступное evidence, явно обозначая недоступную часть основания
