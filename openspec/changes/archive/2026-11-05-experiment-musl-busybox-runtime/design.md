# Design

## Context

См. proposal.md. Текущий экспорт использует glibc ldconfig и пути её конфигурации; musl требует другой конфигурации загрузчика. Portage и ebuild используют Bash и могут требовать GNU-опции отдельных утилит.

## Goals / Non-Goals

Получить проверяемый эксперимент musl + BusyBox и сравнение с glibc. Не менять штатный runtime и не обещать полную совместимость всех ebuild. Bash для Portage сохраняется: BusyBox ash не является заменой языка ebuild.

## Decisions

- Использовать официальный amd64 musl-манифест `edb059ec2a434c504c1f778cff20865abdd40205bbb444ac61f9f9da3bf0aa2e`, snapshot 20261104 с прежним SHA-256 и проверкой подписи.
- Сначала проверить musl с GNU как контроль; затем заменить поддерживаемые BusyBox applets в отдельной конечной файловой системе. Не заменять инструменты в builder.
- Сохранять GNU-исключения только при подтверждённой несовместимости. Честно записывать, какие команды фактически заменены, и отличать гибрид от полного отказа от GNU.
- Сравнивать metadata на одном наборе исходников и профилей с рабочим glibc-runtime; различие среды исполнения не должно подменять профиль анализируемого пакета.
- Экспортные изменения включаются явно для musl. Тесты общего кода и штатный glibc workflow проверяются при затрагивании общего поведения.

## Risks / Trade-offs

- BusyBox поддерживает не все GNU-опции → фиксировать точную ошибку и конкретное исключение, сохранять рабочий контрольный образ.
- Musl может менять поведение Python, Git или sandbox → сравнить metadata, права, сеть и HTTPS.
- Уменьшение размера не гарантировано → измерить оба экспериментальных варианта, не подменять результат обещанием.

## Migration Plan

Миграции нет: эксперимент использует отдельные теги, выбор образа в приёмке явный. Штатный Compose не переключается.
