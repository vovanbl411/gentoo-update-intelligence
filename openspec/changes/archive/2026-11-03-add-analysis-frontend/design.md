## Context

Frontend пока отсутствует. `internal/analysishttp/handler.go` возвращает `{id, result}`,
где `result` содержит `Plan`, `Analysis`, `Reports` с сохранёнными Go-именами полей.
Полный контракт backend остаётся в `docs/http-api.md`. Требования UI заданы в
`specs/analysis-frontend/spec.md`, цель и границы — в `proposal.md`.

План реализации ниже не означает, что frontend или его проверки уже существуют.

## Goals / Non-Goals

**Goals:** отображать сохранённый ответ без повторного Gentoo-анализа; обеспечить
воспроизводимое открытие ссылки и явно показывать неполные данные и ошибки.

**Non-Goals:** менять backend-контракт, запускать обновления, сохранять отметки,
переклассифицировать findings, добавлять Compose, Redis, аутентификацию или публичную
публикацию. Подробности scope перечислены в proposal.

## Decisions

### Отдельный frontend с небольшим стеком

Предлагается `frontend/` с TypeScript, Vite и обычным DOM, без UI framework и router
library. Для двух экранов достаточно небольших модулей формы, API, представления
результата и browser navigation. TypeScript помогает явно описать используемые поля
неоднородных evidence; Vite даёт dev server, proxy и сборку вместо собственного сервера.

Альтернативы: React добавит модель компонентов и зависимости, пока не нужные этому
срезу; Go templates свяжут UI с backend вопреки выбранному разделению frontend/backend.
Версии зависимостей выбираются и закрепляются lock-файлом при реализации.

### Развести browser route и API path

Страница формы — `/`, результата — `/analyses/<uuid>`. Браузер обращается к
`/api/analyses` и `/api/analyses/<uuid>` того же origin. Dev proxy удаляет `/api`
и направляет запрос в Go backend, по умолчанию `http://127.0.0.1:8080`.
Backend продолжает получать существующие `/analyses` и `/analyses/{id}`.

Dev server отдаёт HTML оболочку для прямого открытия browser route. После сборки
сервер публикации должен обеспечивать такой же SPA fallback и proxy, не подменяя
API-ошибки HTML-страницей. Эти требования документируются; реализация production
упаковки и Compose остаётся отдельным change. Проверка прямой ссылки выполняется
на выбранном локальном сервере, а не через `file://`.

### Отправка и загрузка

Форма хранит черновик в памяти страницы. Список пакетов: одна пара на строку,
внешние пробелы строки удаляются, пустые строки пропускаются; из каждой пары
создаётся объект с нижним регистром имён полей `category`, `name`.
Строка плана отправляется без обрезки. Клиентская валидация не заменяет backend.

POST использует `Content-Type: application/json`; `201`, UUID и ожидаемый envelope
проверяются до перехода. Неуспех не очищает форму. POST автоматически не повторяется:
при потере ответа сохранение могло состояться, а идемпотентности в контракте нет.
Сохранение черновика после refresh или закрытия вкладки не входит в срез.

После успеха выполняется переход через History API и GET. Прямой вход, refresh
и Back/Forward используют тот же путь загрузки. GET не зависит от состояния формы
или доступности Metadata Provider для POST. Устаревший ответ GET после смены ID
игнорируется или отменяется; другой анализ не подставляется в текущую страницу.

### Представление ответа без новых правил анализа

Модуль API проверяет envelope и необходимые структурные поля на runtime;
неизвестные дополнительные поля допускаются. Отсутствующие необязательные значения
и `null`-массивы обрабатываются явно, без подстановки нулевых версий или пустого
«успешного» анализа. Нераспознанный статус показывается своим исходным значением.

Карточки пакетов следуют `Plan.Entries`. Связь отчёта определяется `Report.EntryIndex`,
findings — своим `EntryIndex`; значение `0` является корректной ссылкой, `null` — нет.
Findings без записи отображаются отдельно. Для metadata выводятся `Comparison`,
`ComparedFields`, изменения и `Limitations`; причина недоступности берётся из
диагностик связи, Lookup status/Err/SkipReason и Reason соответствующего раздела.
Одинаковые причины можно группировать, сохраняя сторону и исходные коды.

Evidence разрешается по возвращённым индексам: USE groups/tokens, installed
versions и blockers. Номера строк показываются как номера, а не как обещание
исходного текста: API не хранит весь текст плана. `ContextIndex` локальных патчей
сохраняется как основание; исходный список контекста при GET не предполагается
доступным. Неизвестные формы evidence показываются в раскрываемом текстовом JSON.
Такая же текстовая детализация доступна для provenance и диагностик metadata.

UI не вычисляет severity, безопасность обновления или собственные findings.
Содержимое ответа вставляется через текстовые DOM API, без `innerHTML`.
Внешние ресурсы, аналитика и браузерное постоянное хранение плана не нужны.

### Проверки

Для преобразования полей формы, API-ошибок и разрешения evidence предлагается Vitest;
для browser routes, формы и состояний — Playwright с контролируемыми ответами API.
Mock fixtures должны соответствовать сериализации текущего Go API, включая `null`,
blocker findings без EntryIndex, partial и недоступные Lookup outcomes.

Отдельная ручная приёмка использует настоящий backend, PostgreSQL и реальный план
из `testdata/parser/ebuild-updates.txt`. Сравниваются поля UI и JSON POST/GET, а также
новая вкладка и refresh. Предусловие — закреплённый cache-снимок с `dev-libs/libei`
версий `1.6.0` и `1.6.0-r1`, оба Lookup `found` и проверенные SHA-256.
Подготовка снимка и отчётность описаны в задаче 4.3; исходные provenance и commit —
в `docs/metadata-preparation.md`. У документированной пары нет различий в текущих
сравниваемых полях: UI должен отличать доступное сравнение без различий от
недоступных metadata. Непустые изменения проверяются отдельно на fixture.
Сбой сохранения воспроизводится в browser-тесте ответом
`503` без ID; backend-покрытие этого условия уже есть в handler tests.
Реальный прогон не считается выполненным по одному mock-тесту.

## Risks / Trade-offs

- API содержит разные формы evidence без discriminator: явные обработчики текущих
  форм и текстовый fallback сохранят доступные основания при расширении ответа.
- Proxy необходим из-за совпадения путей HTML и JSON: browser-тест прямого входа
  должен отдельно подтвердить HTML оболочку и JSON ответ `/api/analyses/<uuid>`.
- При сетевом сбое POST неизвестно, сохранился ли анализ: UI не обещает обратного
  и допускает только ручной повтор с возможностью создания второго анализа.
- Большие ответы могут перегрузить экран: детали evidence и metadata раскрываются
  по запросу, при этом статусы, findings и причины недоступности остаются видимыми.
- Наличие live backend и PostgreSQL требуется для реальной приёмки; отсутствие
  окружения фиксируется как незавершённая проверка.
