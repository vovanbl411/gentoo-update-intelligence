# Design

## Context

См. proposal.md. Стандартный runtime сейчас musl + GNU, 273 166 632 байта. Worker исполняет egencache с отдельным профилем из закреплённого checkout. Бинарник worker собирается отдельно компилятором Go.

## Goals / Non-Goals

Проверить musl-hardened stage3, сохранить GNU-команды и все существующие сценарии metadata. Не менять профиль запросов на hardened/systemd и не обещать устранение всех уязвимостей. Не менять защитные настройки ядра хоста, Go toolchain, Compose capabilities и сети.

## Decisions

- Взять musl-hardened amd64 digest `44605d8ddaa109d6f60c737713fefe10fa97ea44d50f27fd17c8e25a9c678cf4` вместо смены профиля существующей stage3. Так уже установленные Python и библиотеки берутся из соответствующей сборки.
- Сохранить snapshot 20261104, SHA-256, проверку подписи, atom/USE Git и список runtime-пакетов. Экспорт musl остаётся прежним.
- Сначала собрать candidate base/runtime и builder. Текущие local-теги не менять до функциональной проверки.
- Сравнить ELF-признаки ключевых C-программ: PIE, GNU_STACK, GNU_RELRO, BIND_NOW, символ stack protector и CET notes. Проверять результаты, отмечать совпадения с baseline; не утверждать, что все эти признаки появились только после перехода.
- Отдельно фиксировать, что C-профиль stage3 не пересобирает Go worker. Свойства Go-бинарника не приписываются hardened stage3.
- После приёмки сохранить base/runtime как musl-baseline и опубликовать candidate только в локальные штатные теги. GENTOO_BASE_IMAGE остаётся способом выбора подготовленной базы.

## Risks / Trade-offs

- Hardened USE/CET могут менять совместимость программ → smoke, ELF-аудит и пять metadata-сценариев с побайтовым сравнением.
- У профиля могут оказаться те же измеренные защиты, что у обычной musl stage3 → честно отразить отсутствие изменения конкретных свойств.
- Смена набора файлов stage3 может нарушить экспорт → проверять зависимости, sandbox и отсутствие компилятора/BusyBox в runtime.

## Migration Plan

Проверять отдельные теги, затем выполнить штатную сборку. Для отката использовать сохранённую musl-baseline базу. Рабочие контейнеры и volumes не менять. Удалить собственные временные candidate-теги после сохранения результатов; не очищать общий build cache.
