# analysis-frontend Specification

## Purpose
Позволить пользователю отправить emerge-план через браузер, просмотреть основания
анализа и повторно открыть сохранённый результат по постоянной ссылке.

## Requirements

### Requirement: Ввод плана и локально патченных пакетов
Интерфейс SHALL принимать непустой emerge-план и необязательный список точных
`category/name`, по одному на строку, отправляя данные в существующий POST API.
План SHALL передаваться без изменения его содержимого; пробельный ввод отклоняется.

#### Scenario: Отправка с контекстом
- **WHEN** пользователь отправляет план и две непустые строки `category/name`
- **THEN** запрос содержит исходный `plan` и `locally_patched_packages` с объектами `category` и `name`, в порядке ввода

#### Scenario: Пустой необязательный список
- **WHEN** список пакетов пуст или содержит только пустые строки
- **THEN** запрос не задаёт локально патченные пакеты либо передаёт пустой массив

#### Scenario: Некорректный ввод
- **WHEN** план содержит только пробелы или строка списка не является точным `category/name`
- **THEN** интерфейс показывает ошибку у соответствующего поля, сохраняет ввод и не отправляет запрос

### Requirement: Асинхронное создание и наблюдение за заданием
Интерфейс SHALL переходить на `/analyses/<uuid>` после ответа `202 Accepted` с UUID сохранённого задания. Во время отправки повторная отправка SHALL быть заблокирована; автоматический повтор POST не выполняется. Страница SHALL показывать состояние и прогресс до завершения и затем загружать результат.

#### Scenario: Успешная отправка
- **WHEN** POST возвращает `202 Accepted` с UUID и начальным состоянием
- **THEN** браузер переходит на `/analyses/<uuid>` и запрашивает состояние через GET

#### Scenario: Повторное нажатие
- **WHEN** POST ещё выполняется и пользователь повторно нажимает кнопку отправки
- **THEN** второй POST не создаётся и состояние отправки видно пользователю

#### Scenario: Ожидание и прогресс
- **WHEN** GET сообщает `pending` или `running`
- **THEN** UI показывает состояние, этап и число обработанных запросов и продолжает GET того же UUID

#### Scenario: Завершение и ошибка задания
- **WHEN** GET сообщает `completed` или `failed`
- **THEN** UI показывает итоговый отчёт или возвращённую API причину сбоя и прекращает опрос

#### Scenario: Refresh задания
- **WHEN** пользователь обновляет `/analyses/<uuid>` до завершения задания
- **THEN** UI снова загружает и опрашивает тот же UUID, не создавая новый POST

### Requirement: Повторное открытие сохранённого анализа
Страница `/analyses/<uuid>` SHALL загружать состояние задания через GET и работать
без предшествующей отправки формы. Для незавершённого задания страница SHALL
продолжать наблюдение за тем же UUID; после завершения SHALL показывать сохранённый
результат. Новая вкладка и refresh SHALL сохранять смысл, порядок и значения данных.

#### Scenario: Прямая ссылка и refresh
- **WHEN** пользователь открывает ссылку в новой вкладке или обновляет страницу
- **THEN** загружается соответствующий UUID, а после завершения отображается тот же сохранённый анализ

#### Scenario: Чтение без доступного Metadata Provider
- **WHEN** GET успешно возвращает сохранённый анализ, хотя POST сейчас недоступен
- **THEN** интерфейс показывает результат без нового POST и без повторного анализа

### Requirement: Отображение результата и неполных данных
Интерфейс SHALL показывать возвращённые статусы и диагностики Parser, записи пакетов
с операциями и доступными версиями, findings с категориями и сообщениями, доступный
metadata diff и его ограничения. `partial` и `unsupported` SHALL отображаться как
результаты анализа; отсутствие данных не означает отсутствие изменений или проблем.

#### Scenario: Результат с metadata diff
- **WHEN** API возвращает записи, findings и доступное сравнение metadata
- **THEN** UI показывает их в исходном порядке, включая доступные изменения EAPI, SLOT/SUBSLOT и IUSE без вычисления собственных правил

#### Scenario: Частичный результат
- **WHEN** Parser имеет статус `partial`
- **THEN** UI явно показывает этот статус, диагностики и доступные записи и findings

#### Scenario: Доступное сравнение без различий
- **WHEN** API возвращает доступное сравнение metadata с compared_fields и без изменений в этих полях
- **THEN** UI сообщает об отсутствии различий в сравнённых полях, не обозначая metadata недоступными и не делая вывода об остальных полях

#### Scenario: Неподдерживаемый ввод
- **WHEN** сохранённый результат имеет статус `unsupported` и пустой список пакетов
- **THEN** UI показывает статус и диагностики без сообщения об успешной проверке безопасности обновления

#### Scenario: Недоступные metadata
- **WHEN** API возвращает недоступный раздел, Lookup status, error, skip_reason или diagnostics/limitations
- **THEN** UI показывает доступную причину и сторону before/after там, где она задана API; если причины нет, сообщает только о недоступности данных

### Requirement: Проверяемые основания findings
Интерфейс SHALL связывать findings с возвращёнными API evidence: пакетами, номерами
строк, токенами, установленными версиями, blockers или индексами контекста, насколько
это позволяет ответ. Finding без entry_index SHALL оставаться видимым. Недоступные
фрагменты исходного плана SHALL не восстанавливаться предположениями.

#### Scenario: Основание изменения USE
- **WHEN** finding содержит ссылки на запись и индексы USE-токенов
- **THEN** UI показывает соответствующие возвращённые токены и доступные номера строк

#### Scenario: Blocker без записи пакета
- **WHEN** finding ссылается на blocker_index и не содержит entry_index
- **THEN** UI показывает finding и связанный blocker, не приписывая его произвольной записи

#### Scenario: Неполная ссылка evidence
- **WHEN** возвращённую ссылку нельзя разрешить по данным результата
- **THEN** UI сохраняет finding и доступное evidence, явно обозначая недоступную часть основания

### Requirement: Ошибки отправки и сохранение ввода
При неуспешной отправке интерфейс SHALL сохранять план и список пакетов в форме
текущей страницы, показывать ошибку и позволять ручной повтор. Ошибка запроса,
недоступность сервиса и некорректный ответ SHALL различаться; неподтверждённое
сохранение SHALL не показываться как успешное.

#### Scenario: Сбой сохранения
- **WHEN** POST возвращает `503` без ID
- **THEN** UI показывает недоступность сервиса, сохраняет оба поля и не переходит на страницу результата

#### Scenario: Отклонённый запрос
- **WHEN** POST возвращает `400`, `413` или `415`
- **THEN** UI показывает ошибку отправки с доступным объяснением и сохраняет ввод

#### Scenario: Потеря ответа
- **WHEN** отправка завершается сетевой ошибкой или некорректным успешным ответом
- **THEN** UI сообщает, что сохранение не подтверждено, сохраняет ввод и не повторяет POST автоматически

### Requirement: Ошибки открытия результата
Интерфейс SHALL различать неизвестный UUID, недоступность сервиса и прочие ошибки
загрузки результата. При неуспешном GET SHALL не отображаться результат другого ID.

#### Scenario: Неизвестный UUID
- **WHEN** GET возвращает `404` для неизвестного или некорректного ID
- **THEN** страница сообщает, что анализ не найден, и предлагает перейти к форме

#### Scenario: Сервис недоступен
- **WHEN** GET возвращает `503` или завершается сетевой ошибкой
- **THEN** страница показывает недоступность и позволяет повторить GET для того же ID

### Requirement: Безопасное и доступное представление
Интерфейс SHALL показывать текст API как текст, без выполнения HTML или скриптов,
иметь подписанные поля и доступные с клавиатуры действия. Статусы и ошибки SHALL
передаваться текстом, а не только цветом. Интерфейс SHALL не запускать обновление
системы и не предлагать сохранение отметок или переклассификации в этом срезе.

#### Scenario: Текст с HTML
- **WHEN** сообщение или значение API содержит HTML-разметку
- **THEN** она отображается как текст и не выполняется браузером

#### Scenario: Управление с клавиатуры
- **WHEN** пользователь заполняет форму и открывает результат с клавиатуры
- **THEN** поля, отправка и действия повторной загрузки доступны, а состояния имеют текстовые подписи

### Requirement: Frontend использует DTO v1
Frontend SHALL создавать и читать задания через `/api/v1/analyses` с DTO snake_case и структурированными ошибками. Все состояния, findings, evidence, metadata и причины недоступности SHALL сохранять смысл; страница `/analyses/{id}` и оформление SHALL сохраняться.

#### Scenario: Новый и сохранённый анализ
- **WHEN** пользователь отправляет план или открывает прежний UUID
- **THEN** frontend использует v1, показывает состояние и результат, а запросов к прежнему API не делает

#### Scenario: Неизвестный код ошибки
- **WHEN** API возвращает структурированную ошибку с неизвестным code
- **THEN** frontend показывает её message как текст и сохраняет доступные действия повтора

### Requirement: Компактный отчёт
Интерфейс SHALL показывать сводку полноты разбора, пакетов, findings и доступности metadata и список пакетов в исходном порядке. Список SHALL поддерживать поиск по имени, фильтры и вывод порциями по 50 записей.

#### Scenario: Большой план
- **WHEN** результат содержит более 50 пакетов
- **THEN** интерфейс показывает первые 50 и позволяет показать следующие с учётом поиска и фильтра

### Requirement: Читаемые подробности
Интерфейс SHALL показывать findings и их основания, изменения EAPI, SLOT, SUBSLOT и IUSE, а также ограничения и причины недоступности без необходимости читать JSON.

#### Scenario: Частичное сравнение
- **WHEN** сравнение доступно только частично
- **THEN** интерфейс показывает имеющиеся изменения и ограничения, не делая вывод об остальных полях

#### Scenario: Finding без пакета
- **WHEN** finding не связан с записью пакета
- **THEN** интерфейс показывает его отдельно с доступным основанием

### Requirement: Технические данные по запросу
Интерфейс SHALL получать компактный отчёт при открытии задания и загружать полный JSON только по запросу пользователя. Пользователь SHALL иметь возможность скачать полный JSON.

#### Scenario: Открытие отчёта
- **WHEN** пользователь открывает результат
- **THEN** полный endpoint не вызывается до запроса технических данных

### Requirement: Постепенное отображение отчёта
Интерфейс SHALL показывать доступные факты и готовые сравнения до завершения задания, обозначать ожидающие metadata как подготавливаемые и автоматически обновлять отчёт и прогресс.

#### Scenario: Сравнение ещё готовится
- **WHEN** промежуточный отчёт содержит ожидающую запись
- **THEN** интерфейс показывает её как подготавливаемую, не как ошибку или отсутствие изменений

### Requirement: Отображение пересборок
UI SHALL показывать R как «Пересборка» с целевой версией. При отсутствии установленной стороны SHALL явно сообщать, что она не указана и сравнение до/после недоступно.

#### Scenario: Пересборка без установленной версии
- **WHEN** результат содержит reinstall с пустым installed
- **THEN** карточка показывает Пересборка, target и отсутствие установленной стороны без выдуманной before

### Requirement: Явная полнота разбора
Для Parser partial или unsupported UI SHALL показывать заметное предупреждение, что анализ охватывает только распознанные записи и отсутствие findings не характеризует весь вход. Сводка SHALL называться «Распознано пакетов»; общий счётчик SHALL показываться только при наличии сводки Portage.

#### Scenario: Прежний частичный результат
- **WHEN** открыт сохранённый partial или unsupported
- **THEN** UI показывает предупреждение, распознанное количество и общий счётчик только из summary без автоматического повторного анализа

### Requirement: Независимое ограничение metadata
Ограниченность metadata comparison SHALL обозначаться отдельно от полноты разбора.

#### Scenario: Полный разбор с недоступным сравнением
- **WHEN** Parser parsed, но metadata comparison недоступно
- **THEN** UI отдельно обозначает ограничение сравнения и не называет разбор неполным
