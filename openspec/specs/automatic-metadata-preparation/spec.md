# automatic-metadata-preparation Specification

## Purpose
Обеспечить автоматическую подготовку воспроизводимых metadata для анализа пользовательского плана обновления Gentoo.

## Requirements

### Requirement: Синхронизация дерева
Gentoo-контейнер SHALL автоматически синхронизировать основное дерево при запуске с пустым volume и повторять попытку через три часа после завершения предыдущей, сохраняя данные в постоянном volume.

#### Scenario: Первый запуск
- **WHEN** сервис запускается с пустым volume и источник доступен
- **THEN** синхронизация создаёт пригодное для анализа состояние без ручной подготовки снимка

#### Scenario: Ошибка очередной синхронизации
- **WHEN** синхронизация после успешной попытки завершается ошибкой
- **THEN** сервис продолжает анализ с последним успешным состоянием и не публикует частичное обновление

#### Scenario: Нет успешного состояния
- **WHEN** первоначальная синхронизация не удалась и успешного состояния нет
- **THEN** сервис сообщает о недоступности подготовки, не выдавая частичное дерево за успешное состояние

### Requirement: Закреплённые репозитории
Каждый анализ SHALL использовать закреплённые полные ревизии всех необходимых репозиториев и сохранять их в provenance результата. Синхронизация SHALL не менять ревизии выполняющегося анализа.

#### Scenario: Обновление во время анализа
- **WHEN** синхронизация публикует новую ревизию во время анализа
- **THEN** все обращения этого анализа используют ранее закреплённые ревизии

### Requirement: Подготовка по плану
Сервис SHALL определять необходимые репозитории и точные версии из плана, загружать известные оверлеи по требованию и переиспользовать уже загруженные репозитории.

#### Scenario: Повторный план
- **WHEN** повторный анализ требует уже доступный оверлей
- **THEN** сервис переиспользует его без повторной полной загрузки

### Requirement: Обновление загруженных оверлеев
Перед каждым новым анализом, которому нужен загруженный оверлей, сервис SHALL автоматически пытаться обновить его из доверенного источника. Сервис SHALL публиковать только проверенную полную ревизию атомарно и сохранять последнюю успешную ревизию при ошибке обновления. Закреплённые ревизии выполняющихся анализов SHALL оставаться доступными.

#### Scenario: Новая версия оверлея
- **GIVEN** оверлей уже загружен и в его источнике опубликована новая версия пакета
- **WHEN** новый анализ запрашивает эту версию и автоматическое обновление успешно
- **THEN** анализ использует новую опубликованную ревизию и получает доступ к версии без ручного обновления или повторного полного клонирования

#### Scenario: Ошибка обновления оверлея
- **GIVEN** у оверлея есть последняя успешно опубликованная ревизия
- **WHEN** автоматическое обновление завершается ошибкой
- **THEN** новый анализ использует последнюю успешную ревизию, а частичное обновление не публикуется

### Requirement: Доверенный каталог репозиториев
Сервис SHALL поддерживать расширение доверенного каталога настройкой оператора, которая явно сопоставляет имена репозиториев с URL и необходимыми masters. URL из пользовательского плана SHALL NOT использоваться для загрузки. Если имя неизвестно или неоднозначно, соответствующая сторона записи SHALL содержать явную причину отсутствия сравнения.

#### Scenario: Репозитории реального плана
- **GIVEN** оператор настроил записи `gentoo-zh` и `umbriel-overlay` с URL и необходимыми masters
- **WHEN** план ссылается на эти имена
- **THEN** сервис разрешает их через настроенный каталог и закрепляет ревизии репозиториев и masters

#### Scenario: Неизвестное имя
- **WHEN** имя репозитория из плана отсутствует в каталоге
- **THEN** сервис не угадывает URL и указывает причину для соответствующей стороны записи

### Requirement: Получение точных metadata
Сервис SHALL использовать готовый cache точной версии, а при его отсутствии применять существующие resolver и генератор, если доступны исходники и необходимые master repositories. Результат SHALL содержать provenance использованных metadata и исходников.

#### Scenario: Готовый cache
- **WHEN** cache точной версии доступен в закреплённой ревизии или совместимом сохранённом результате
- **THEN** сервис использует его без повторной генерации и показывает источник

#### Scenario: Генерация
- **WHEN** cache отсутствует, но точный ebuild и необходимые master repositories доступны
- **THEN** сервис готовит metadata точной версии и сохраняет provenance для повторного использования

### Requirement: Частичный отчёт
Ошибка подготовки отдельного пакета SHALL не прерывать обработку остальных записей. Для каждой записи отчёт SHALL показывать доступный diff с источниками либо конкретную причину отсутствия сравнения.

#### Scenario: Недоступные данные
- **WHEN** оверлей неизвестен, история недоступна, master repository отсутствует или генерация завершается ошибкой
- **THEN** соответствующая запись содержит конкретную причину и сторону сравнения, а остальные записи попадают в отчёт

### Requirement: Ограничение работы
Сервис SHALL дедуплицировать совпадающие запросы подготовки и ограничивать параллельную генерацию настраиваемым положительным пределом.

#### Scenario: Большой план
- **WHEN** план из 1000 или более записей содержит повторяющиеся запросы
- **THEN** одинаковая подготовка выполняется один раз для совместимого набора входов, а число одновременных генераций не превышает настроенный предел

#### Scenario: Повтор запроса внутри анализа
- **WHEN** один анализ обращается за metadata с одинаковым полным Query несколько раз, в том числе после завершения предыдущего Lookup
- **THEN** Provider вызывается один раз для этого Query, а результат или ошибка сохраняются во всех соответствующих записях отчёта

### Requirement: Состояние анализа
Сервис SHALL предоставлять сохранённый идентификатор и состояние обработки, прогресс и итоговый результат для повторного чтения. Сбой обработки SHALL быть виден с причиной.

#### Scenario: Обработка продолжается
- **WHEN** клиент запрашивает состояние принятого, но не завершённого анализа
- **THEN** ответ содержит состояние и прогресс завершённых и общего числа уникальных metadata `Query`

#### Scenario: Повторяющиеся запросы в прогрессе
- **WHEN** несколько записей плана используют одинаковые metadata `Query`
- **THEN** каждый уникальный `Query` входит в общее число прогресса один раз и увеличивает завершённое число после одного Lookup

#### Scenario: Завершение
- **WHEN** обработка завершается
- **THEN** результат доступен по тому же идентификатору и сохраняет отчёт и provenance

#### Scenario: Восстановление после рестарта
- **GIVEN** задание не завершилось до рестарта сервиса и его ревизии уже закреплены
- **WHEN** сервис восстанавливает задание
- **THEN** обработка возобновляется с ранее закреплёнными ревизиями либо задание завершается с явной причиной невозможности восстановления

#### Scenario: Рестарт до закрепления ревизий
- **GIVEN** принятое задание не закрепило ревизии до рестарта сервиса
- **WHEN** сервис восстанавливает задание
- **THEN** обработка возобновляется с этапа выбора ревизий либо задание завершается с явной причиной невозможности восстановления

#### Scenario: Ранее сохранённый анализ
- **GIVEN** результат анализа сохранён до перехода на асинхронные задания
- **WHEN** клиент запрашивает его по прежнему идентификатору
- **THEN** сервис возвращает сохранённый результат со статусом `completed`

### Requirement: Очередь анализов с настраиваемым пределом
Один backend SHALL ограничивать число активных анализов: по умолчанию `1`, положительное целое задаёт предел, `0` отключает ограничение. Ожидающие задания SHALL храниться в PostgreSQL как `pending/queued` без Parser, Provider и отдельной goroutine на задание. Принятие SHALL сохранять `202` и UUID; выбор SHALL идти по `created_at, id`. Независимый положительный лимит генераций metadata SHALL оставаться `2` по умолчанию.

#### Scenario: Все слоты заняты
- **GIVEN** один анализ выполняется при пределе `1`
- **WHEN** API принимает ещё один план
- **THEN** новый UUID возвращается без ожидания завершения первого анализа, а новое задание остаётся `pending/queued` и не обращается к Provider до освобождения слота

#### Scenario: Несколько слотов или отключённый предел
- **WHEN** предел установлен в `2` или `0` и приняты несколько заданий
- **THEN** одновременно запускается не больше двух анализов при `2`, а при `0` очередь не ограничивает число активных анализов

#### Scenario: Восстановление очереди
- **GIVEN** в базе есть `pending` и прерванные `running`, в том числе с закреплёнными ревизиями
- **WHEN** единственный backend перезапускается
- **THEN** незавершённые задания поступают в общую очередь, обрабатываются в пределах лимита и сохраняют прежние закреплённые ревизии

#### Scenario: Ошибка отдельного задания или очереди
- **WHEN** задание заканчивается ошибкой либо чтение очереди временно недоступно
- **THEN** конечная ошибка задания освобождает слот для следующего, а ошибка чтения повторяется без потери принятых заданий и без запуска второго диспетчера

### Requirement: Ранние и постепенные результаты
Parser и Analyzer SHALL выполняться до подготовки репозиториев; их результаты SHALL сохраняться как промежуточный отчёт. Готовые результаты metadata SHALL сохраняться под тем же UUID в порядке плана, а после рестарта обработка SHALL использовать сохранённые закреплённые ревизии.

#### Scenario: Длительная подготовка
- **WHEN** metadata одного пакета ещё готовятся
- **THEN** ранее готовые результаты и факты плана доступны без ожидания этого пакета

#### Scenario: Восстановление
- **WHEN** backend перезапускается после закрепления ревизий
- **THEN** отчёт остаётся доступен, а обработка продолжается с сохранёнными ревизиями
