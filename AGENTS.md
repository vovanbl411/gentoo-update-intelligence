## Границы работы

- Для новых функциональных изменений сначала прочитай [docs/openspec.md](docs/openspec.md) и относящиеся к задаче активные changes в `openspec/changes/`. Веди артефакты согласованной задачи через `sh scripts/openspec.sh`; мелкие изменения без влияния на контракт не требуют отдельного change.
- Выполняй порученный этап и останавливайся после его завершения.
- Архитектурные изменения вне согласованной задачи сначала выноси на обсуждение.
- Предпочитай минимальное решение. Добавляй зависимости, компоненты и рефакторинг, только если они решают конкретную задачу в пределах порученного scope.

## Рабочее дерево

- Проверяй состояние репозитория перед изменениями.
- Сохраняй чужие изменения; не откатывай и не перезаписывай их.
- Несвязанные изменения сами по себе не требуют остановки. При прямом конфликте с задачей сообщи о нём.

## Проверки

- Проверяй изменённое поведение подходящими проверками проекта.
- Для Parser, Analyzer, metadata diff, ChangeReport, Metadata Provider, reportservice и planservice запускай команды из `backend/`: `gofmt` для изменённых Go-файлов, `go test -count=1 ./...` и `go vet ./...`.
- Для CLI запускай команды из `backend/`: `gofmt` для изменённых Go-файлов, `go test -count=1 ./...`, `go vet ./...` и `go build -o /tmp/gentoo-update-intelligence ./cmd/gentoo-update-intelligence`.
- Выполняй `git diff --check` для изменённых tracked-файлов. Новые untracked-файлы также проверяй на whitespace.
- Не заявляй о проверках, которые не запускались, и не придумывай команды сборки и тестирования. Добавь такие команды, когда появится реализация.
- После успешных проверок не расширяй задачу без новых оснований.

## Документация

- Пиши понятным техническим языком на русском, сохраняя технические идентификаторы на английском.
- Различай принятые решения, планы и реализованное состояние.
- Обновляй документацию, затронутую изменением, в пределах порученной задачи.

## Git и отчёт

- Выполняй commit, push и merge только по явному поручению.
- Не меняй настройки Git и подписи.
- В отчёте указывай изменения, выполненные проверки и оставшиеся ограничения, а также diff или commit для review.
- Отличай подтверждённые проблемы от предположений.

## Навигация по коду через CodeGraph

- Для локальных запросов используй `sh scripts/codegraph.sh`: скрипт отключает телеметрию, автоматическое скачивание и фоновый демон. Не вызывай CodeGraph напрямую или через MCP в обход скрипта.
- Если `.codegraph/` существует, перед поиском поведения кода и цепочек вызовов выполни `sh scripts/codegraph.sh explore "<вопрос>"`. Проверяй вывод по исходникам; для точных строк и конфигурации используй `rg`.
- Перед `explore`, `query`, `context`, `node`, `files`, `callers`, `callees`, `impact` и `affected` скрипт автоматически выполняет `sync --quiet`. При ошибке обновления запрос не запускается; используй `rg` и исходники. Отдельный `sync` после редактирования, `git pull` или переключения ветки не требуется: индекс обновится при следующем запросе.
- Не запускай запросы к графу одновременно с изменением исходников: обновление перед запросом не защищает от изменений во время его выполнения.
- Проверяй состояние командой `sh scripts/codegraph.sh status`. Если индекса нет, не создавай его без разрешения пользователя; используй `rg`.
- `codegraph.json` задаёт исключения чувствительных файлов и каталогов. Локальный индекс `.codegraph/` исключён из Git. Не расширяй область индексации за пределы репозитория.
