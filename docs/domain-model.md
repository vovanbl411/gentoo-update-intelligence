# Контракт предметной модели

Документ фиксирует логический контракт данных для проектирования и review. Это не SQL-схема и не готовый API. Указанные сущности и связи описывают требуемый смысл данных; физическое представление может быть определено отдельно.

## Общие правила

- PostgreSQL хранит `Analysis`, связанные с ним результаты и записи `Evidence`. Redis используется только как восстанавливаемый кэш: его удаление не теряет пользовательские данные и сохранённые результаты.
- Поля с условной обязательностью обязательны только при названном условии. Необязательное поле может отсутствовать; отсутствие само по себе не означает пустой список или установленное отсутствие факта.
- `evidence_refs` содержат ID записей `Evidence`, а не копии основания. Происхождение пользовательских утверждений должно оставаться различимым от вычисленных фактов.
- Время задаётся backend или сервисом в момент соответствующего события. Идентификаторы назначает backend.

## Analysis

Один `Analysis` — сохранённый разбор конкретного входного плана, предоставленного пользовательского контекста и версий инструментов анализа. После завершения исходный вход и вычисленный результат не перезаписываются. Повторный расчёт создаёт новый `Analysis`. Решение пользователя хранится отдельно от вычисленного результата и относится к конкретному анализу.

| Поле | Смысл и источник | Обязательность и хранение |
|---|---|---|
| `id` | Идентификатор анализа; назначает backend. | Обязательно; сохраняется в PostgreSQL. |
| `created_at` | Время создания анализа; назначает backend. | Обязательно; сохраняется в PostgreSQL. |
| `input` | Исходный текст плана и предоставленный пользователем контекст. Источник — пользовательский ввод. | Текст плана обязателен, дополнительный контекст необязателен. Сохраняется в PostgreSQL; исходное содержимое также представлено соответствующим `Evidence`. |
| `processing_status` | Состояние обработки, которое ведёт backend. | Обязательно; сохраняется в PostgreSQL. Допустимые значения определены ниже. |
| `completed_at` | Время окончания обработки, в том числе неудачной. Назначает backend после окончания. | Заполняется после завершения обработки; до этого отсутствует. Сохраняется в PostgreSQL. |
| `parser_version` | Версия Parser, зафиксированная до начала обработки. | Обязательна; сохраняется в PostgreSQL. |
| `rule_set_version` | Версия набора правил, зафиксированная до начала обработки. | Обязательна; сохраняется в PostgreSQL. |
| `diff_engine_version` | Версия реализации сравнения, которую использовал Diff Engine. | Обязательна, если выполнялось сравнение; иначе отсутствует. Сохраняется в PostgreSQL. |
| `metadata_sources` | Фактически использованные источники metadata и их ревизии. Источник — выполненная обработка. | Список обязателен и может быть пустым; сохраняется в PostgreSQL. |
| `limitations` | Ограничения разбора и недоступные данные, выявленные при обработке. | Список обязателен и может быть пустым; сохраняется в PostgreSQL. |
| `failure` | Причина технического сбоя обработки. Источник — backend. | Обязательна при `failed`; в остальных статусах отсутствует. Сохраняется в PostgreSQL. |

`processing_status` принимает значения:

- `processing` — обработка выполняется;
- `completed` — обработка завершена; findings и ограничения допустимы;
- `failed` — обработка не завершилась из-за технического сбоя.

Значение `pending` не вводится без очереди. Статус обработки не кодирует полноту результата или approval. Недоступность дополнительных upstream notes сама по себе не переводит анализ в `failed`. Результаты Parser `parsed`, `partial` и `unsupported` не добавляются в `Analysis.processing_status`; неподдерживаемый вход сам по себе не является техническим сбоем. Контракт Parser v0.1 описан в [документе Parser](parser.md).

`PackageChange`, `Finding` и `ChangeReport` связываются с анализом через `analysis_id`.

## PackageChange

Один `PackageChange` — запланированное действие Portage над конкретным пакетом в рамках одного анализа. Имя пакета не уникально: план может содержать разные SLOT или несколько действий для одного пакета. Запись принадлежит одному `Analysis` и не переиспользуется между анализами.

| Поле | Смысл и источник | Обязательность и хранение |
|---|---|---|
| `id` | Идентификатор изменения; назначает backend. | Обязательно; сохраняется в PostgreSQL. |
| `analysis_id` | ID содержащего запись анализа. | Обязательно; сохраняется в PostgreSQL. |
| `package` | Имя пакета в форме `category/name`; извлекается из входа. | Обязательно; сохраняется в PostgreSQL. |
| `operation` | Действие Portage, установленное по входу. | Обязательно; сохраняется в PostgreSQL. Значения перечислены ниже. |
| `before` | Известное состояние пакета до действия, подтверждённое входом или идентифицированными данными. | Может быть неизвестно полностью или частично; известные факты сохраняются в PostgreSQL вместе с различимым состоянием неизвестного значения. |
| `after` | Известное целевое состояние пакета, подтверждённое входом или идентифицированными данными. | Может быть неизвестно полностью или частично; хранится по тем же правилам, что и `before`. |
| `use_changes` | Явно установленные из входа изменения USE. | Необязательное поле со значимым различием между неизвестностью и известным пустым списком; хранится в PostgreSQL. |
| `evidence_refs` | Ссылки на фрагменты плана, подтверждающие изменение. | Обязателен непустой список ID `Evidence`; ссылки хранятся вместе с записью в PostgreSQL. |

Состояния `before` и `after` могут включать `version`, `slot`, `subslot`, `repository` и `effective USE` — только в той мере, в которой значения подтверждены входом или данными с установленным происхождением. Неизвестные значения нельзя восстанавливать предположениями.

`operation` принимает значения `install`, `upgrade`, `downgrade`, `rebuild`, `remove` или `unknown`. `remove` допустим только при явном указании удаления в поддерживаемом входе. Наличие значения в словаре модели не означает, что Parser сразу поддерживает все варианты. В Parser v0.1 операция `NS` означает установку в новый SLOT: показанная рядом установленная версия — контекст, а не свидетельство замены или удаления старого пакета, и `before` не подтверждает установленную версию именно в целевом SLOT. Блокировка зависимости — это `Finding`, а не операция. См. [контракт Parser v0.1](parser.md).

Известный пустой список USE-изменений отличается от неизвестного списка. Категория внимания, локальные патчи и объяснение причин USE не являются фактами Parser: их отражают `Finding` или `ChangeReport` в пределах соответствующих оснований.

## Finding

`Finding` — конкретный вывод детерминированного правила с проверяемым основанием.

| Поле | Смысл и источник | Обязательность и хранение |
|---|---|---|
| `id` | Идентификатор вывода; назначает backend. | Обязательно; сохраняется в PostgreSQL. |
| `analysis_id` | ID анализа, в котором вычислен вывод. | Обязательно; сохраняется в PostgreSQL. |
| `package_change_ids` | ID затронутых изменений пакетов. | Список обязателен; пустой для вывода уровня `Analysis`, может включать несколько ID. Сохраняется в PostgreSQL. |
| `rule_id` | Идентификатор применённого правила. | Обязателен; сохраняется в PostgreSQL. |
| `code` | Машинный код конкретного вывода. | Обязателен; сохраняется в PostgreSQL. |
| `category` | Категория внимания, назначенная по правилам. | Обязательна; сохраняется в PostgreSQL. |
| `message` | Объяснение конкретного вывода. | Обязательно; сохраняется в PostgreSQL. |
| `evidence_refs` | Ссылки на основания вывода. | Обязателен непустой список ID `Evidence`; ссылки хранятся вместе с записью в PostgreSQL. |

Версия набора правил берётся из `Analysis` и отдельно в `Finding` не дублируется. Категории имеют следующий смысл:

- `BLOCKER` — подтверждённое препятствие выполнению плана;
- `SECURITY` — связь с подтверждённой информацией о безопасности;
- `CONFLICT` — подтверждённая несовместимость или противоречие, требующее разрешения;
- `REVIEW` — требуется проверка или решение пользователя;
- `NORMAL` — информационный вывод без отдельного подтверждения.

Категории не образуют линейную шкалу severity. `SECURITY` может сообщать об исправлении уязвимости и само по себе не означает остановку обновления. Условия назначения категорий определяются правилами; их влияние на approval согласовано не полностью.

Для одного `PackageChange` допустимо несколько findings. Отсутствие findings не доказывает безопасность: необходимо учитывать `limitations` анализа. Для каждого пакета автоматически создавать `NORMAL` finding не требуется. Решение пользователя не изменяет исходный finding. Findings не переиспользуются между анализами.

## ChangeReport

На один `PackageChange` приходится один `ChangeReport`. Он показывает различия; необходимость внимания интерпретируется в findings.

| Поле | Смысл и источник | Обязательность и хранение |
|---|---|---|
| `id` | Идентификатор отчёта; назначает backend. | Обязательно; сохраняется в PostgreSQL. |
| `analysis_id` | ID анализа, в котором выполнено сравнение. | Обязательно; сохраняется в PostgreSQL. |
| `package_change_id` | ID изменения пакета, к которому относится отчёт. | Обязательно; сохраняется в PostgreSQL. |
| `gentoo_diff` | Раздел сравнения Gentoo metadata, ebuild и Gentoo patches. | Присутствует всегда, включая состояния `unavailable` и `not_applicable`; сохраняется в PostgreSQL. |
| `effective_config_diff` | Раздел сравнения известных изменений эффективной конфигурации пользователя и подтверждённых причин. | Присутствует всегда; сохраняется в PostgreSQL. |
| `upstream_changes` | Раздел найденной upstream-информации. | Присутствует всегда; сохраняется в PostgreSQL. |

Каждый раздел всегда содержит обязательные `status`, `changes`, `evidence_refs` и `limitations`. Источник статуса и результата — выполненное сравнение; `evidence_refs` указывают на подтверждающие записи `Evidence`, а `limitations` — на ограничения этого сравнения. Все четыре поля сохраняются в PostgreSQL вместе с отчётом. `status` принимает значения:

- `available` — сравнение выполнено в заявленных границах;
- `partial` — получена часть результата;
- `unavailable` — необходимых данных или возможности обработки нет;
- `not_applicable` — сравнение неприменимо.

При `available` и пустом `changes` различия отсутствуют только в проверенных данных. Это не означает, что у пакета нет любых изменений. Недоступный раздел нельзя выдавать за проверенный пустой результат.

`gentoo_diff` содержит структурированные `before`/`after` для согласованных metadata, различия ebuild и набора Gentoo patches. Сравниваются идентифицированные версии из конкретных ревизий источников. Возможная область сравнения описана в [архитектуре](architecture.md); первый реализуемый набор metadata пока не выбран.

`effective_config_diff` содержит известные изменения эффективных USE и подтверждённые причины. Он ссылается на факты `PackageChange` без полного дублирования этой сущности.

`upstream_changes` содержит release notes, changelog, security notes и другие найденные сведения. У каждого элемента указываются источники и охватываемые версии. Заметки об одном релизе не считаются полным обзором диапазона версий.

Отсутствие `before` при `install` само по себе не является ошибкой. Применимость сравнения определяется отдельно.

## Evidence

`Evidence` хранится отдельно; `evidence_refs` ссылаются на записи по ID. Запись должна позволять различить вычисленные факты и пользовательские утверждения.

| Поле | Смысл и источник | Обязательность и хранение |
|---|---|---|
| `id` | Идентификатор основания; назначает backend. | Обязательно; запись и сохранённое содержимое относятся к сохраняемым данным PostgreSQL. |
| `kind` | Тип происхождения: пользовательский ввод, Gentoo metadata или upstream source. | Обязателен; сохраняется вместе с записью `Evidence`. |
| `source` | Идентификатор сохранённого входа или адрес источника. | Обязателен; сохраняется вместе с записью `Evidence`. |
| `locator` | Строки входа, путь файла, поле или раздел документа. | Указывается, когда применимо; сохраняется вместе с записью `Evidence`. |
| `revision` | Commit, версия или другой идентификатор состояния источника. | Указывается, если предоставляется источником; сохраняется вместе с записью `Evidence`. |
| `content_hash` | Хеш сохранённого содержимого. | Нужен для сохранённого содержимого; хранится вместе с записью `Evidence`. Хеш не заменяет само содержимое. |
| `captured_at` | Время получения данных сервисом. | Обязательно; сохраняется вместе с записью `Evidence`. |

Физическое размещение содержимого пока не выбирается. Для детерминированных findings сохраняется основание, позволяющее повторно проверить вывод: исходный текст или использованное содержимое metadata вместе с происхождением. Для дополнительного upstream enrichment допустима внешняя ссылка без сохранённого содержимого; ограничение воспроизводимости в этом случае обозначается явно.

## Неизвестные значения

Для значения, которое может быть неизвестно или неприменимо, логически различаются состояния:

- `known` — значение установлено;
- `unknown` — значение установить не удалось;
- `unavailable` — необходимый источник недоступен;
- `not_applicable` — значение неприменимо.

Пустое значение не заменяет эти состояния. Известный пустой список изменений означает, что сравнение выполнено и изменений в проверенных данных нет. Обязательные `id`, `package` и `created_at` не оборачиваются в эти состояния. Точную JSON-форму и единый способ кодирования пока не выбираем.

Статус раздела `ChangeReport` и состояние отдельного поля относятся к разным уровням. Например, `before.slot` может иметь состояние `unknown`, а `effective_config_diff` — `unavailable` из-за недостатка данных.

## Хранение и повторное использование

PostgreSQL сохраняет `Analysis`, связанные результаты и `Evidence`. Redis — восстанавливаемый кэш; его удаление не теряет пользовательские данные и сохранённые результаты.

Общий Gentoo diff допустимо переиспользовать при совпадении пакета, обеих версий, необходимых ревизий источников и версии алгоритма сравнения. Точный физический ключ пока не проектируется. Пользовательская конфигурация и findings в общий diff не входят.

Воспроизводимость оценивается по частям результата:

- для Parser нужны вход и версия Parser;
- для Analyzer — использованные факты и версия набора правил;
- для Diff Engine — исходные metadata и версия алгоритма.

## Сквозной пример

Пример условный и не описывает реальный анализ пакета.

Пусть `sys-kernel/gentoo-kernel` обновляется с условной версии `1.0` до условной версии `1.1`. Пользователь указал, что у него есть локальные патчи. Gentoo metadata обеих сторон доступны, данных для сравнения пользовательской конфигурации недостаточно, а upstream notes получить не удалось.

Результат может выглядеть так:

- `Analysis` имеет статус `completed` и `limitations`, указывающие на недостаток данных для сравнения пользовательской конфигурации и недоступность upstream notes.
- `PackageChange` содержит `operation: upgrade` и подтверждённые входом состояния до и после.
- `Finding` с кодом `LOCAL_PATCHED_PACKAGE` и категорией `REVIEW` ссылается на план и пользовательское указание о локальных патчах. Он требует проверить применимость патчей, но не утверждает, что они сломаются.
- `ChangeReport.gentoo_diff` имеет статус `available`; `effective_config_diff` и `upstream_changes` имеют статус `unavailable`.

Неизвестные USE не считаются отсутствием изменений. Повторный расчёт с дополнительными данными создаёт новый `Analysis`. Approval остаётся отдельным контрактом.

## Открытые вопросы

- Поддерживаемый вход и поведение Parser, включая полностью неподдерживаемый вход.
- Точная форма представления неизвестных значений и единый способ их кодирования.
- Физическая схема хранения и API.
- Первый реализуемый набор metadata для Diff Engine.
- Точные правила findings и переходы review/approval.
