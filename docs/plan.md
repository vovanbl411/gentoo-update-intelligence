# План разработки

Этапы задают последовательность проектирования и реализации. Будущие результаты описаны как план, а не как уже принятые или готовые решения.

| 3. Parser | Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. | 5. Ограниченный Gentoo metadata diff, ChangeReport и Metadata Provider | Контракт и реализация первого среза metadata diff приняты после review коммита `cc4574e` и подтверждения локальных проверок. Контракт и реализация локального Metadata Provider приняты после review коммита `2babded` и подтверждения локальных проверок. Provider читает точную запись закреплённого commit локального Git-репозитория и передаёт содержимое в `metadatadiff.Normalize`; его проверки подтверждают закрепление commit, безопасное точное чтение, provenance, обработку ошибок и отсутствие изменений репозитория. Реальные downgrade fixtures пока не предоставлены; направление downgrade проверяется синтетическим сценарием. |

Реальная first-parent история `libei` подтверждает выбор обеих версий; детали приведены в [контракте подготовки metadata](metadata-preparation.md). |
| 7. Генерация metadata из выбранной ревизии | `internal/metadatagenerator` принят после review коммита `666beaa`. | Тесты с локальной заглушкой проверяют точный cache, ошибки команды, неверный ebuild SHA/содержимое и отсутствие нужной версии. Реальный прогон на Gentoo проходит через resolver, `egencache`, Git-снимок и существующий CLI; provenance и SHA-256 сверяются с Lookup. Master repositories для оверлеев и публичный API генерации остаются отдельными этапами. |
| 8. HTTP API и постоянное хранение анализа | `POST /analyses` и `GET /analyses/{id}` реализованы по [контракту HTTP API](http-api.md) с использованием `planservice`, Metadata Provider и PostgreSQL. | Полный результат, включая статусы и ошибки Lookup, успешно сохранён и прочитан по тому же ID после перезапуска backend с недоступным Provider на PostgreSQL 18; JSON POST и GET равен; ошибка записи не выдаёт ID или `201`; неизвестный ID даёт `404`. |
| 9. Остальная интеграция | Добавить минимальный frontend и Docker Compose; использовать Redis только для конкретных кэшируемых обращений. | Сценарий проходит через frontend и backend; удаление кэша не теряет сохранённые данные. |
| 10. Полный сценарий | Проверить путь пользователя от ввода до повторного открытия сохранённого результата. | Проходит сценарий: ввод → анализ → diff/evidence → решение пользователя → повторное открытие результата. |

## Текущее состояние: backend API и постоянное хранение анализа реализованы

Этап 2 принят после review коммита `9c35e3b`. Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. Реализация находится в `internal/parser`; fixture и отрицательные сценарии покрыты тестами. Контракт и реализация Analyzer v0.1 приняты после review коммита `097685a` и подтверждения проверок. Контракт и реализация первого среза metadata diff приняты после review коммита `cc4574e` и подтверждения локальных проверок; код находится в `internal/metadatadiff`. Ограниченный ChangeReport принят после review коммита `6af5e05` и подтверждения локальных проверок; реализация и тесты находятся в `internal/changereport`. Контракт и реализация локального Metadata Provider приняты после review коммита `2babded` и подтверждения локальных проверок; код и тесты находятся в `internal/metadataprovider`. Контракт и реализация reportservice в [docs/report-service.md](report-service.md) приняты после review коммита `1396782` и подтверждения локальных проверок. Поддержка downgrade принята после review `d290539`; blockers и удаления — после review `a38074f`. Реальные downgrade и blocker fixtures пока не предоставлены; соответствующие сценарии проверяются синтетическими входами. Planservice принят после review `013523e`, его контракт описан в [docs/plan-service.md](plan-service.md). Полный сервис и интеграция Analyzer внутрь reportservice не реализованы.

Предупреждения о пропущенных обновлениях из-за dependency conflict остаются отдельным отложенным этапом и ограничением Parser. Контракт минимального CLI описан в [docs/cli.md](cli.md); реализация принята после review коммита `a7d794e`. Открытые вопросы модели, не относящиеся к Parser, сохраняются в [контракте предметной модели](domain-model.md).

Контракт выбора исторической ревизии ebuild принят после review `a9a7a42`; resolver принят после review `6716bdc`, а `internal/metadatagenerator` — после review `666beaa`. Реальный прогон подтвердил выбор `1.6.0` в `88a930a…` и `1.6.0-r1` в reference `f7cf26b…`, генерацию обоих cache, их Lookup в существующем CLI и сравнение перехода `1.6.0 → 1.6.0-r1`. Подробные хеши и ограничения checkout указаны в [контракте подготовки metadata](metadata-preparation.md).

HTTP API и PostgreSQL-хранение реализованы по [контракту HTTP API](http-api.md). Сквозной прогон на PostgreSQL 18 подтвердил создание анализа по реальному emerge plan, чтение того же JSON после перезапуска backend с недоступным Metadata Provider и `404` для неизвестного UUID. Подэтап не включает frontend, Redis, Compose или генерацию metadata по HTTP.

Validation gate Parser, Analyzer, metadata diff, planservice, resolver и CLI: `gofmt` для изменённых Go-файлов, `go test -count=1 ./...`, `go vet ./...`, `go build -o /tmp/gentoo-update-intelligence ./cmd/gentoo-update-intelligence` и `git diff --check`; metadata diff проверяет SHA-256 реальных fixtures, EAPI 8, SLOT/SUBSLOT, IUSE, статусы и evidence. Parser извлекает только подтверждённые входом факты, Analyzer сохраняет статус и диагностики Parser и связывает findings с проверяемыми основаниями. planservice сохраняет результаты компонентов и проверяется на синтетических сценариях и временном локальном Git-репозитории; CLI проверяется через функцию запуска и локальные синтетические репозитории; resolver проверяется на локальных синтетических Git-репозиториях.
