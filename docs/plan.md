# План разработки

## Текущее состояние

Сервис проходит полный пользовательский путь: отправка плана через frontend или HTTP API, фоновый анализ, просмотр отчёта и повторное открытие по UUID. Локальный Compose включает backend, frontend, PostgreSQL, синхронизацию Gentoo и metadata worker. Redis не подключён.

Один backend по умолчанию выполняет один анализ, а metadata worker — не больше двух генераций одновременно. Ожидающие задания хранятся в PostgreSQL. Лимит анализов настраивается вплоть до отключения (`0`); предел генераций остаётся положительным. Настройка и порядок применения описаны в [руководстве Compose](local-compose.md#число-активных-анализов). Несколько backend с общей очередью пока не поддерживаются.

Реализованное поведение описано в [архитектуре](architecture.md) и контрактах компонентов. Результаты прежних сквозных проверок, включая чистые volumes, повторный анализ и план из 1000 записей, сохранены в [отчёте приёмки](../frontend/acceptance.md). Это история проверок, а не обещание производительности или доступности metadata для любого пакета.

HTTP API переведён на `/api/v1/analyses` с отдельными DTO snake_case и структурированными ошибками. Сохранённые результаты читаются через адаптер без миграции. Контракт — в [спецификации API](../openspec/specs/http-api/spec.md).

Backend поддерживает YAML-конфигурацию без пересборки при изменении файла, с приоритетом непустых env и ранней проверкой. Поля и применение — в [руководстве backend](backend-configuration.md).

## Выполненные этапы

| Этап | Результат | Основание проверки |
|---|---|---|
| 1. Первоначальная документация | Зафиксированы назначение, архитектурные границы и последовательность работ. | Документы и ограничения проекта. |
| 2. Контракт данных | Принята логическая модель `Analysis`, `PackageChange`, `Finding`, `ChangeReport`, `Evidence`. | [Предметная модель](domain-model.md); физическая схема и API описываются отдельно. |
| 3. Parser | Реализован разбор поддерживаемых строк, статусы полноты и диагностика. | [Контракт Parser](parser.md), реальные fixtures и синтетические отрицательные сценарии. |
| 4. Analyzer | Реализованы правила с evidence, включая downgrade и неразрешённые blockers. | [Контракт Analyzer](analyzer.md), тесты правил и ограничений неполного входа. |
| 5. Metadata diff и отчёты | Сравнение EAPI 8, SLOT/SUBSLOT и IUSE; ChangeReport, локальный Provider, reportservice и planservice. | Контракты компонентов; реальные metadata fixtures с provenance и SHA-256, синтетические планы и временные Git-репозитории. |
| 6. Выбор ревизии ebuild | Resolver выбирает точный ebuild в reference или его first-parent истории. | [Подготовка metadata](metadata-preparation.md): синтетические Git-сценарии и реальная история `libei`. |
| 7. Генерация metadata | Generator и metadata worker подключены к HTTP; сохраняются provenance и файловый cache. | Тесты генератора, реальный прогон `libei`, Compose-приёмка с master repositories. |
| 8. HTTP API и хранение | Асинхронный POST возвращает `202`; GET показывает состояние и результат. Задания и закреплённые ревизии сохраняются в PostgreSQL и восстанавливаются после перезапуска. | [Контракт HTTP API](http-api.md), тесты и приёмка асинхронного анализа. |
| 9. Интеграция | Приняты frontend и локальный Compose с автоматической подготовкой metadata. | [Инструкция Compose](local-compose.md), [спецификации OpenSpec](openspec.md) и отчёт приёмки. Redis остаётся отложенным. |
| 10. Полный сценарий | Проверены ввод плана, просмотр diff/evidence и повторное открытие сохранённого результата. | [Отчёт приёмки frontend](../frontend/acceptance.md). |

## Ограничения и следующие задачи

Следующий функциональный этап выбирается отдельно. Перечень ниже не задаёт новый согласованный scope или порядок реализации:

Предложения по ускорению анализа, отмене, истории заданий и идентификации пользователей собраны в [backlog](backlog.md).

- Предупреждения о пропущенных обновлениях из-за dependency conflict остаются ограничением Parser.
- Реальных downgrade и blocker fixtures пока нет; эти сценарии проверяются синтетическими входами.
- Metadata diff ограничен EAPI, SLOT/SUBSLOT и IUSE; effective configuration и upstream остаются `unavailable`.
- Findings Analyzer остаются отдельно от reportservice; approval не реализован.
- Redis, расширение сравнений и эксплуатационные решения остаются отложенными; подробности — в [архитектуре](architecture.md).

## Проверки при изменениях

Обязательные проверки заданы в [AGENTS.md](../AGENTS.md). Для изменений Go-компонентов команды выполняются из `backend/`: `gofmt` для изменённых Go-файлов, `go test -count=1 ./...` и `go vet ./...`; для CLI дополнительно выполняется `go build -o /tmp/gentoo-update-intelligence ./cmd/gentoo-update-intelligence`. Также требуется `git diff --check` и проверка whitespace новых файлов.

Команды frontend приведены в [его руководстве](../frontend/README.md). Приёмочные результаты следует отличать от локальных unit-тестов: синтетические репозитории не подтверждают доступность конкретных версий в реальной истории Gentoo.
