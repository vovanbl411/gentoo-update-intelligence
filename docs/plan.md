# План разработки

Этапы задают последовательность проектирования и реализации. Будущие результаты описаны как план, а не как уже принятые или готовые решения.

## Этапы

| Этап | Цель и результат | Validation gate |
|---|---|---|
| 1. Первоначальная документация | Зафиксировать назначение, baseline архитектуры v0.1 и последовательность работ. | Документы согласованы между собой; ограничения и открытые вопросы явно указаны. |
| 2. Контракт данных | Логический контракт `Analysis`, `PackageChange`, `Finding`, `ChangeReport` и `Evidence` в `docs/domain-model.md` принят после review коммита `9c35e3b`. | Контракт описывает назначение, поля, источники, обязательность, evidence, неизвестные значения, хранение и воспроизводимость; оставшиеся вопросы перечислены явно. |
| 3. Parser | Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. Реализация и тесты подготовлены. | Контракт задаёт подтверждённые входом факты, правила `parsed` / `partial` / `unsupported`, диагностики и границы поддержки; проверки проходят на неизменённом fixture и отрицательных сценариях. |
| 4. Analyzer | Контракт и реализация Analyzer v0.1 приняты после review коммита `097685a` и подтверждения проверок. | Правила не подменяют факты Parser; findings объяснимы и опираются на проверяемые evidence; ограничения неполного входа видны. |
| 5. Ограниченный Gentoo metadata diff | Контракт принят после review коммита `42ac7ed`. Реализация первого среза и тесты подготовлены и ожидают review; полный `ChangeReport` не реализован. | EAPI 8, SLOT / SUBSLOT и IUSE нормализуются и сравниваются с evidence и ограничениями; реальный fixture проверяет происхождение и SHA-256. |
| 6. Интеграция | Соединить API, PostgreSQL, минимальный frontend и Docker Compose; использовать Redis для конкретных кэшируемых обращений. | Сохранённый анализ читается через backend; удаление кэша не теряет сохранённые данные. |
| 7. Полный сценарий | Проверить путь пользователя от ввода до повторного открытия сохранённого результата. | Проходит сценарий: ввод → анализ → diff/evidence → решение пользователя → повторное открытие результата. |

## Текущее состояние: Parser и Analyzer приняты, metadata diff подготовлен к review

Этап 2 принят после review коммита `9c35e3b`. Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. Реализация находится в `internal/parser`; fixture и отрицательные сценарии покрыты тестами. Контракт и реализация Analyzer v0.1 приняты после review коммита `097685a` и подтверждения проверок. Контракт metadata diff из [документа metadata diff](metadata-diff.md) принят после review коммита `42ac7ed`; реализация первого среза находится в `internal/metadatadiff`, а тесты покрывают реальные и синтетические сценарии. Код и документация ожидают review. Полный `ChangeReport` и интеграция с Analyzer остаются вне реализации этого этапа.

Следующий шаг — review реализации первого среза Gentoo metadata diff. Открытые вопросы модели, не относящиеся к Parser, сохраняются в [контракте предметной модели](domain-model.md).

Validation gate Parser, Analyzer и metadata diff: `gofmt` для изменённых Go-файлов, `go test ./...`, `go vet ./...` и `git diff --check`; metadata diff проверяет SHA-256 реальных fixtures, EAPI 8, SLOT/SUBSLOT, IUSE, статусы и evidence. Parser извлекает только подтверждённые входом факты, Analyzer сохраняет статус и диагностики Parser и связывает findings с проверяемыми основаниями.
