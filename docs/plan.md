# План разработки

Этапы задают последовательность проектирования и реализации. Будущие результаты описаны как план, а не как уже принятые или готовые решения. Документация этого этапа ещё не отмечена как принятая пользователем.

## Этапы

| Этап | Цель и результат | Validation gate |
|---|---|---|
| 1. Первоначальная документация | Зафиксировать назначение, baseline архитектуры v0.1 и последовательность работ. | Документы согласованы между собой; ограничения и открытые вопросы явно указаны. |
| 2. Контракт данных | Согласовать `Analysis`, `PackageChange`, `Finding`, `ChangeReport` и подготовить `docs/domain-model.md`. Подробности ближайшего этапа приведены ниже. | Для сущностей определены источники данных, обязательность, `unknown` / `unavailable`, evidence, хранение, кэширование и воспроизводимость; неразрешённые решения отмечены. |
| 3. Parser | Выбрать поддерживаемый формат, подготовить реальные fixtures, реализовать извлечение фактов и проверить его на fixtures, включая неполный и неподдерживаемый вход. | Parser извлекает только подтверждённые входом факты; неполные и неподдерживаемые случаи дают явный результат. |
| 4. Analyzer | Согласовать небольшой набор детерминированных правил, evidence для findings и контракт review/approval; реализовать согласованные правила и проверить ожидаемые findings на примерах. | Правила не подменяют факты Parser; выводы объяснимы; поведение review/approval согласовано. |
| 5. Ограниченный ChangeReport | Реализовать первое сравнение на Gentoo metadata с проверяемыми ревизиями и воспроизводимым результатом. | Для результата идентифицируются входные данные и ревизии metadata; ограничения отсутствующих данных видны пользователю. |
| 6. Интеграция | Соединить API, PostgreSQL, минимальный frontend и Docker Compose; использовать Redis для конкретных кэшируемых обращений. | Сохранённый анализ читается через backend; удаление кэша не теряет сохранённые данные. |
| 7. Полный сценарий | Проверить путь пользователя от ввода до повторного открытия сохранённого результата. | Проходит сценарий: ввод → анализ → diff/evidence → решение пользователя → повторное открытие результата. |

## Ближайший этап: контракт данных

Результат этапа — отдельный документ `docs/domain-model.md` с согласованным контрактом данных. До его подготовки требуется определить границы и смысл каждой сущности, не превращая предварительные названия из архитектуры в схему по умолчанию.

Для `Analysis`, `PackageChange`, `Finding` и `ChangeReport` нужно зафиксировать:

- назначение сущности, связи и источник каждого поля;
- обязательные и условные поля, а также различие между отсутствующим, неизвестным и недоступным значением;
- формат и жизненный цикл evidence: сохраняется ли содержимое или ссылка, какие идентификаторы и ревизии нужны для проверки вывода;
- какие данные сохраняются в PostgreSQL, а какие разрешено кэшировать в Redis; удаление Redis не должно удалять пользовательские данные;
- какие версии parser и набора правил, исходные данные и ревизии metadata требуются для воспроизводимости;
- при каких условиях можно повторно использовать вычисленный package-version diff и как проверить совместимость сохранённого результата с текущими версиями источников.

Особое внимание нужно уделить данным, которых может не быть во входном плане. Модель должна позволять отличить неизвестное значение от отсутствующего источника или неподдерживаемого входа. Она не должна заставлять Parser выводить severity, причины USE-изменений или рекомендации.

Validation gate этапа: документ покрывает все перечисленные вопросы и согласован с baseline архитектуры. Спорные поля, правила повторного использования и детали хранения остаются явно открытыми, пока для них нет решения. После согласования контракта можно уточнить формат parser fixtures и границы первого ChangeReport.
