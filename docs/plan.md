# План разработки

Этапы задают последовательность проектирования и реализации. Будущие результаты описаны как план, а не как уже принятые или готовые решения.

## Этапы

| Этап | Цель и результат | Validation gate |
|---|---|---|
| 1. Первоначальная документация | Зафиксировать назначение, baseline архитектуры v0.1 и последовательность работ. | Документы согласованы между собой; ограничения и открытые вопросы явно указаны. |
| 2. Контракт данных | Логический контракт `Analysis`, `PackageChange`, `Finding`, `ChangeReport` и `Evidence` в `docs/domain-model.md` принят после review коммита `9c35e3b`. | Контракт описывает назначение, поля, источники, обязательность, evidence, неизвестные значения, хранение и воспроизводимость; оставшиеся вопросы перечислены явно. |
| 3. Parser | Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. Реализация и тесты подготовлены. | Контракт задаёт подтверждённые входом факты, правила `parsed` / `partial` / `unsupported`, диагностики и границы поддержки; проверки проходят на неизменённом fixture и отрицательных сценариях. |
| 4. Analyzer | Контракт и реализация Analyzer v0.1 приняты после review коммита `097685a` и подтверждения проверок. | Правила не подменяют факты Parser; findings объяснимы и опираются на проверяемые evidence; ограничения неполного входа видны. |
| 5. Ограниченный Gentoo metadata diff, ChangeReport и Metadata Provider | Контракт и реализация первого среза metadata diff приняты после review коммита `cc4574e` и подтверждения локальных проверок. Ограниченный `ChangeReport` принят после review коммита `6af5e05` и подтверждения локальных проверок. Контракт и реализация локального Metadata Provider приняты после review коммита `2babded` и подтверждения локальных проверок. Реализация reportservice принята после review коммита `1396782` и подтверждения локальных проверок. Расширение downgrade принято после review `d290539`; поддержка blockers и удалений — после review `a38074f`. | EAPI 8, SLOT / SUBSLOT и IUSE сравниваются с evidence и ограничениями; реальные fixtures проверяют provenance и SHA-256. ChangeReport связывает выбранную запись плана со снимками, сохраняет результат `Compare` и формирует три независимых раздела. Provider читает точную запись закреплённого commit локального Git-репозитория и передаёт содержимое в `metadatadiff.Normalize`; его проверки подтверждают закрепление commit, безопасное точное чтение, provenance, обработку ошибок и отсутствие изменений репозитория. Проверки reportservice подтверждают точные запросы, порядок вызовов, сохранение исходов Lookup, блокировку запросов при неподдерживаемой записи и неизвестном коде диагностики связи, а также интеграцию с локальным Provider. planservice объединяет существующие компоненты для целого плана и сохраняет отдельные результаты Parser, Analyzer и отчёты по записям. Реальные downgrade fixtures пока не предоставлены; направление downgrade проверяется синтетическим сценарием. |
| 6. Выбор исходной ревизии ebuild | Контракт принят после review `a9a7a42`. Реализация `internal/ebuildresolver` с синтетическими тестами подготовлена к review. | Синтетические Git-репозитории проверяют выбор reference commit и ancestor, удаление и повторное добавление файла, first-parent merge, немонотонные даты, shallow-границы, корень полной истории, ошибки Git и повторяемость без изменений repository. Локальная проверка `libei` ограничена shallow-границей checkout; детали приведены в [контракте подготовки metadata](metadata-preparation.md). |
| 7. Генерация metadata из выбранной ревизии | Отдельный этап после resolver: получить cache точной версии через `egencache` и подготовить Git-снимок для существующего Provider. Генератор не реализован. | Ebuild и eclasses берутся из selected commit; необходимые master repositories закреплены; из пакетной генерации выбирается точный `metadata/md5-cache/category/name-version`; provenance и SHA-256 проверяются; Provider читает готовый снимок без генерации. |
| 8. Интеграция | Соединить API, PostgreSQL, минимальный frontend и Docker Compose; использовать Redis для конкретных кэшируемых обращений. | Сохранённый анализ читается через backend; удаление кэша не теряет сохранённые данные. |
| 9. Полный сценарий | Проверить путь пользователя от ввода до повторного открытия сохранённого результата. | Проходит сценарий: ввод → анализ → diff/evidence → решение пользователя → повторное открытие результата. |

## Текущее состояние: planservice и CLI приняты; resolver ожидает review

Этап 2 принят после review коммита `9c35e3b`. Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. Реализация находится в `internal/parser`; fixture и отрицательные сценарии покрыты тестами. Контракт и реализация Analyzer v0.1 приняты после review коммита `097685a` и подтверждения проверок. Контракт и реализация первого среза metadata diff приняты после review коммита `cc4574e` и подтверждения локальных проверок; код находится в `internal/metadatadiff`. Ограниченный ChangeReport принят после review коммита `6af5e05` и подтверждения локальных проверок; реализация и тесты находятся в `internal/changereport`. Контракт и реализация локального Metadata Provider приняты после review коммита `2babded` и подтверждения локальных проверок; код и тесты находятся в `internal/metadataprovider`. Контракт и реализация reportservice в [docs/report-service.md](report-service.md) приняты после review коммита `1396782` и подтверждения локальных проверок. Поддержка downgrade принята после review `d290539`; blockers и удаления — после review `a38074f`. Реальные downgrade и blocker fixtures пока не предоставлены; соответствующие сценарии проверяются синтетическими входами. Planservice принят после review `013523e`, его контракт описан в [docs/plan-service.md](plan-service.md). Полный сервис и интеграция Analyzer внутрь reportservice не реализованы.

Предупреждения о пропущенных обновлениях из-за dependency conflict остаются отдельным отложенным этапом и ограничением Parser. Контракт минимального CLI описан в [docs/cli.md](cli.md); его реализация подготовлена и ожидает review. Открытые вопросы модели, не относящиеся к Parser, сохраняются в [контракте предметной модели](domain-model.md).

Контракт выбора исторической ревизии ebuild принят после review `a9a7a42`; реализация resolver подготовлена к review. Генератор metadata не реализован. На локальном checkout эксперимента `libei` проверена версия `1.6.0-r1`; выбор для `1.6.0` не завершён из-за подтверждённой shallow-границы.

Validation gate Parser, Analyzer, metadata diff, planservice, resolver и CLI: `gofmt` для изменённых Go-файлов, `go test -count=1 ./...`, `go vet ./...`, `go build -o /tmp/gentoo-update-intelligence ./cmd/gentoo-update-intelligence` и `git diff --check`; metadata diff проверяет SHA-256 реальных fixtures, EAPI 8, SLOT/SUBSLOT, IUSE, статусы и evidence. Parser извлекает только подтверждённые входом факты, Analyzer сохраняет статус и диагностики Parser и связывает findings с проверяемыми основаниями. planservice сохраняет результаты компонентов и проверяется на синтетических сценариях и временном локальном Git-репозитории; CLI проверяется через функцию запуска и локальные синтетические репозитории; resolver проверяется на локальных синтетических Git-репозиториях.
