# План разработки

Этапы задают последовательность проектирования и реализации. Будущие результаты описаны как план, а не как уже принятые или готовые решения.

## Этапы

| Этап | Цель и результат | Validation gate |
|---|---|---|
| 1. Первоначальная документация | Зафиксировать назначение, baseline архитектуры v0.1 и последовательность работ. | Документы согласованы между собой; ограничения и открытые вопросы явно указаны. |
| 2. Контракт данных | Логический контракт `Analysis`, `PackageChange`, `Finding`, `ChangeReport` и `Evidence` в `docs/domain-model.md` принят после review коммита `9c35e3b`. | Контракт описывает назначение, поля, источники, обязательность, evidence, неизвестные значения, хранение и воспроизводимость; оставшиеся вопросы перечислены явно. |
| 3. Parser | Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. Реализация и тесты подготовлены. | Контракт задаёт подтверждённые входом факты, правила `parsed` / `partial` / `unsupported`, диагностики и границы поддержки; проверки проходят на неизменённом fixture и отрицательных сценариях. |
| 4. Analyzer | Контракт Analyzer v0.1 подготовлен и ожидает review. Реализации ещё нет. | Правила не подменяют факты Parser; findings объяснимы и опираются на проверяемые evidence; ограничения неполного входа видны. |
| 5. Ограниченный ChangeReport | Реализовать первое сравнение на Gentoo metadata с проверяемыми ревизиями и воспроизводимым результатом. | Для результата идентифицируются входные данные и ревизии metadata; ограничения отсутствующих данных видны пользователю. |
| 6. Интеграция | Соединить API, PostgreSQL, минимальный frontend и Docker Compose; использовать Redis для конкретных кэшируемых обращений. | Сохранённый анализ читается через backend; удаление кэша не теряет сохранённые данные. |
| 7. Полный сценарий | Проверить путь пользователя от ввода до повторного открытия сохранённого результата. | Проходит сценарий: ввод → анализ → diff/evidence → решение пользователя → повторное открытие результата. |

## Текущее состояние: Parser принят, контракт Analyzer ожидает review

Этап 2 принят после review коммита `9c35e3b`. Контракт Parser v0.1 принят после review коммита `cd49426` и подтверждения локальных проверок. Реализация находится в `internal/parser`; fixture и отрицательные сценарии покрыты тестами. Контракт Analyzer v0.1 описан в [документе Analyzer](analyzer.md), подготовлен и ожидает review; Analyzer ещё не реализован.

Следующий шаг — review контракта Analyzer и согласование конкретного представления Go-типов и ссылок на пользовательский контекст перед реализацией. Открытые вопросы модели, не относящиеся к Parser, сохраняются в [контракте предметной модели](domain-model.md).

Validation gate реализации Parser: `go test ./...` и `go vet ./...` проходят; Parser извлекает только подтверждённые входом факты, а неполные и неподдерживаемые случаи дают явный результат.
