# Контракт первого среза Gentoo metadata diff

Документ задаёт контракт сравнения двух подготовленных снимков metadata. Получение и проверка источников относятся к Metadata Provider. Diff Engine не скачивает данные и не выполняет ebuild. Автоматическую синхронизацию Provider пока не проектируем и не реализуем. Контракт не задаёт Go-типы, JSON API или SQL.

## Границы сравнения

Первый срез сравнивает только `EAPI`, `SLOT` / `SUBSLOT` и `IUSE` для одного и того же `category/name` и имени репозитория. Сравниваемые версии и ревизии источника могут различаться. Пара с разными пакетами или именами репозиториев не сравнивается.

Поддерживается только EAPI 8. Исходное значение EAPI сохраняется и отдельно проверяется на поддержку. Если хотя бы одна сторона использует неподдерживаемый EAPI, поля нельзя интерпретировать по правилам EAPI 8. Контракт не предполагает совместимость семантики разных EAPI.

Сравнение выбранных состояний репозитория не доказывает, что такие metadata использовались при сборке установленного у пользователя пакета. Имя репозитория, к которому относится пакет, хранится отдельно от URL зеркала, откуда получены данные.

В этот срез не входят зависимости, `REQUIRED_USE`, `LICENSE`, `SRC_URI`, diff ebuild, Gentoo patches, effective configuration, upstream notes, findings и approval.

## Снимок

Каждая сторона сравнения — подготовленный снимок, который логически содержит:

- `category/name`, версию и имя репозитория;
- URL источника, commit и путь cache-файла;
- SHA-256 полного сохранённого содержимого и это исходное содержимое как evidence;
- нормализованные поля, полученные из сохранённого содержимого;
- диагностики отсутствующих или некорректных данных.

Содержимое снимка сохраняется целиком. Его нельзя заменять выбранными строками, сортировать или нормализовать пробелы и табуляцию. В происхождении отдельно фиксируются repository name и зеркало. SHA-256 относится ко всем байтам локального snapshot; Git blob SHA и значение `_md5_` внутри cache-файла имеют другой смысл и не заменяют этот хеш.

## Нормализация полей

### EAPI

Сохраняется исходное значение и проверяется поддержка. Сравнивать его семантику по правилам EAPI 8 можно только для поддерживаемого EAPI. Неподдерживаемое значение нельзя молча трактовать как `8`.

### SLOT и SUBSLOT

Сохраняются исходная строка `SLOT`, нормализованные `SLOT` и `SUBSLOT`, а также признак, был ли `SUBSLOT` указан явно. Для EAPI 8 значение без `/` означает, что `SUBSLOT` равен `SLOT`.

Сравниваются нормализованные значения. Поэтому переход исходной строки `2` → `2/2` не считается изменением `SLOT` или `SUBSLOT`; различие исходного представления остаётся доступным через evidence. Изменение `SUBSLOT` само по себе не задаёт конкретный список пакетов, которые пользователь должен пересобрать.

### IUSE

Из каждой записи выделяются имя флага и объявленный default:

- `foo` — default явно не объявлен;
- `+foo` — default явно включён;
- `-foo` — default явно выключен.

Порядок токенов не влияет на смысл сравнения. Результаты сортируются по имени флага. Добавленные и удалённые флаги отражаются отдельно. Изменение default отражается отдельно только для флагов, присутствующих с обеих сторон. Например, `foo` → `-foo` — изменение объявления default, но не доказательство изменения состояния флага у пользователя.

`IUSE=` — известный пустой список. Отсутствующий ключ `IUSE` означает, что поле недоступно. Отсутствующее или повреждённое значение нельзя считать пустым списком или удалением флагов. Некорректные значения и противоречивые дубликаты не исправляются молча; они дают диагностики и не используются как достоверное значение поля.

Удаление флага из `IUSE` не доказывает, что флаг был включён в конфигурации пользователя.

## Статус результата

Логический результат содержит `status`, `compared_fields`, `changes`, `limitations` и ссылки на оба снимка. Точные типы ссылок и представление результата пока не выбираются.

| `status` | Значение |
|---|---|
| `available` | Сравнены все три группы: EAPI, SLOT / SUBSLOT и IUSE. |
| `partial` | Сравнена только часть групп. |
| `unavailable` | Сравнение выполнить не удалось. |

`compared_fields` перечисляет фактически сравнённые поля, включая поля без различий. Пустой `changes` означает только отсутствие различий в этих полях. `limitations` объясняет, почему остальные поля сравнить не удалось. Внутренний контракт не использует статус `not_applicable`; применимость общего `ChangeReport` определяется отдельно.

Каждое изменение содержит значения before/after и evidence обеих сторон. Для EAPI, SLOT и SUBSLOT изменения показывают before и after. Для IUSE отдельно указываются добавленные и удалённые флаги и изменения default у общих флагов. Отсутствующее или недостоверное значение не создаёт изменение удаления.

## План проверок реализации

Следующие сценарии нужно покрыть при реализации. Это план, а не отчёт о выполненных тестах:

- реальный fixture из [`testdata/metadata`](../testdata/metadata/provenance.md);
- отсутствие различий;
- только перестановка токенов IUSE;
- добавление и удаление флагов;
- переходы default между отсутствующим, `+` и `-`;
- явный и неявный SUBSLOT, включая равнозначное представление `2` и `2/2`;
- отсутствующий ключ IUSE и присутствующий пустой `IUSE=`;
- некорректные значения и противоречивые дубликаты;
- неподдерживаемый EAPI;
- несовпадающие package или имя репозитория;
- частично доступные поля.

Синтетические случаи проверяют обработку входных снимков и не являются реальными repository metadata.

## Открытые вопросы перед реализацией

- Конкретные Go-типы и представление результатов в API и SQL.
- Механизм Metadata Provider для проверки источника и подготовки снимков; автоматическая синхронизация остаётся вне scope.
- Точные коды и структура диагностик для отсутствующих, некорректных и противоречиво повторённых полей.
- Точное формирование `status`, `compared_fields` и `limitations` при сочетании поддерживаемых и неподдерживаемых либо повреждённых полей.
