# Контракт внутреннего reportservice

`internal/reportservice` — будущий внутренний слой координации между одной записью Parser, локальным Metadata Provider и существующим `changereport.Build`. Это не сетевой сервис. Контракт описывает ожидаемое поведение; пакет и интеграция ещё не реализованы.

## API

Будущий пакет предоставляет узкий интерфейс Provider и функцию сборки отчёта:

```go
type MetadataLookup interface {
	Lookup(metadataprovider.Query) (metadataprovider.LookupResult, error)
}

func Build(
	plan parser.Result,
	entryIndex int,
	provider MetadataLookup,
) (Result, error)

type Result struct {
	Report       changereport.Report
	BeforeLookup LookupOutcome
	AfterLookup  LookupOutcome
}
```

`LookupOutcome` содержит необязательные точный `Query` и исходный `metadataprovider.LookupResult`, ошибку `Lookup`, если она возникла, и `SkipReason`, если вызов не выполнялся. Точные Go-типы этих полей и `SkipReason` остаются открытыми до реализации.

## Outcome Lookup

Каждый исход сохраняет достаточно данных, чтобы отличить пропущенный запрос, штатный ответ Provider и ошибку чтения:

| Сценарий | Query | Result | Err | SkipReason |
|---|---|---|---|---|
| Lookup не выполнялся (`not_requested`) | отсутствует | отсутствует | отсутствует | заполнен |
| Lookup выполнен успешно | точный запрос | исходный результат Provider | отсутствует | пуст |
| Lookup завершился ошибкой | точный запрос | отсутствует | исходная ошибка с сохранённой цепочкой обёрток | пуст |

При успешном вызове сохраняется статус Provider без преобразования: `found`, `not_found` или `repository_unavailable`. Ошибка Provider, включая `metadataprovider.ErrRead`, остаётся ошибкой, распознаваемой через `errors.Is`. Нельзя объединять `not_found`, `repository_unavailable` и ошибку чтения в один исход.

Для не выполненного вызова используется `not_requested`, выраженный заполненным `SkipReason`; отдельное дублирующее поле статуса не добавляется. При ошибке одной стороны её outcome сохраняет соответствующий запрос и ошибку, а обработка второй стороны продолжается.

## Алгоритм сборки

1. Сначала вызвать `changereport.Build(plan, entryIndex, nil, nil)`. Этот предварительный вызов проверяет индекс и применяет действующие проверки операции, установленного контекста, repository и другие правила связи. Без snapshots он не выполняет `metadatadiff.Compare`.
2. Если индекс некорректен, вернуть ошибку, распознаваемую как `changereport.ErrInvalidEntryIndex` через `errors.Is`. Не вызывать Provider, не допускать panic и не выбирать другую запись.
3. Для допустимого индекса требуется переданный Provider. При его отсутствии вернуть распознаваемую ошибку настройки вызова. Точное имя ошибки и обработка интерфейса с typed-nil остаются открытыми до реализации.
4. Разрешить Lookup только если предварительный отчёт содержит диагностики и каждая из них имеет код `changereport.CodeSnapshotMissing` (`SNAPSHOT_MISSING`). При наличии любой другой диагностики не вызывать Lookup ни для одной стороны, вернуть предварительный `Report` и заполнить оба `SkipReason` объяснением отказа. Предварительная проверка должна быть закрытой по умолчанию: новый или неизвестный `BindingCode` не разрешает Lookup. Не воспроизводить отдельно проверки операции, `InstalledContext`, repository или другие проверки `ChangeReport`.
5. Сформировать точные запросы из выбранной записи:
   - `before`: `Package` записи, версия и repository единственного установленного контекста;
   - `after`: `Package` записи, целевая версия и repository.
6. Вызвать один и тот же Provider последовательно, сначала для `before`, затем для `after`. Не выполнять повторные попытки или fallback. Ошибка первого вызова не отменяет второй.
7. Только snapshot из результата со статусом `found` передать в повторный `changereport.Build`. Для `not_found`, `repository_unavailable` и ошибки соответствующий snapshot отсутствует.
8. Вернуть окончательный `Report` и оба `LookupOutcome`.

Повторный `changereport.Build` остаётся владельцем проверки, что найденные snapshots соответствуют записи: `Package`, версия, repository и применимые SLOT/SUBSLOT. Reportservice не изменяет и не фильтрует `Comparison`, не заменяет диагностики Parser результатами Lookup и не дублирует правила связи.

Неизвестная диагностика предварительного отчёта блокирует запросы так же, как любая другая диагностика, отличная от `SNAPSHOT_MISSING`. Это правило должно быть покрыто тестом, чтобы добавление нового кода `BindingCode` не расширило разрешённый набор неявно.

## Отчёт и ограничения результата

Если предварительная проверка запрещает запросы, итогом служит предварительный `Report`; обе стороны имеют `not_requested` с объяснением. Если запросы выполнялись, результатом служит отчёт повторного `changereport.Build` с snapshots только для найденных сторон.

Диагностика `SNAPSHOT_MISSING` в `Report` показывает, что снимок отсутствует. `LookupOutcome` рядом объясняет причину: точная версия не найдена, repository не обслуживается или чтение завершилось ошибкой. Контракт `changereport.Build` при этом не меняется.

Если Lookup завершился ошибкой, отчёт не объявляется полностью проверенным или безопасным. Findings Analyzer остаются отдельными: reportservice не принимает, не создаёт и не изменяет их. Approval в этот контракт не входит.

## Границы и безопасность

- Вызывающий код заранее открывает и передаёт Provider.
- Reportservice не выбирает и не меняет commit и не открывает другие providers.
- Reportservice самостоятельно не выполняет сетевые запросы или Git-команды.
- Он не читает файлы и не выполняет ebuild.
- Контракт не вводит постоянные ID, время, API или хранение.
- Входные структуры не изменяются.

## Будущие проверки

Тестовая реализация `MetadataLookup` должна позволять проверить:

- точность двух запросов, порядок `before` → `after` и количество вызовов;
- `found` для обеих сторон;
- `not_found` и `repository_unavailable` по каждой стороне;
- ошибку `before` при успешном `after`, успешный `before` при ошибке `after` и ошибки обеих сторон;
- сохранение `errors.Is` и точных запросов в ошибочных outcomes;
- пропуск Lookup для неподдерживаемой записи;
- запрет запросов при диагностике, отличной от `SNAPSHOT_MISSING`, в том числе при неизвестном `BindingCode`;
- некорректный индекс и отсутствие Provider;
- сохранение Parser partial и его диагностик;
- отказ повторного `Build` связывать полученные чужие snapshots;
- неизменность входных структур;
- зависимость предварительной проверки от кодов `BindingCode` и закрытое поведение для нового кода отказа.

Отдельный тест должен пройти цепочку: небольшой временный Git-репозиторий с синтетическими cache-данными → реальный Metadata Provider → reportservice → `ChangeReport` с синтетическим Parser-планом. Тест не использует сеть и не клонирует Gentoo; синтетические данные теста не следует описывать как реальные Gentoo metadata.

Эти сценарии являются планом будущей проверки; они не заявляются как выполненные.

## Открытые вопросы до реализации

- Точные Go-типы `LookupOutcome` и `SkipReason`.
- Распознаваемая ошибка при отсутствии Provider и обработка typed-nil interface.
- Поведение при нарушении контракта реализацией `MetadataLookup`, например при статусе `found` без `Snapshot`.
