# Работа с OpenSpec

OpenSpec подключён как пилот для следующих согласованных функциональных изменений.
Перенос всех контрактов и выбор следующего этапа разработки в подключение не входят.
Изменения без влияния на контракт, например небольшие исправления документации,
можно выполнять без отдельного OpenSpec change.

## Источники требований

- `docs/architecture.md` сохраняет общие архитектурные решения, `docs/plan.md` — этапы.
- Существующие контракты в `docs/` остаются основными источниками требований своих областей.
- `openspec/specs/<область>/spec.md` становится основным источником требований только для новой или явно перенесённой области.
- `openspec/changes/<изменение>/` содержит предлагаемое изменение, а не подтверждение реализации.
- Код, тесты и результаты проверок подтверждают реализованное состояние.

При переносе области укажи это в proposal и одновременно обнови прежний документ:
замени перенесённые требования ссылкой на спецификацию, сохранив полезные пояснения.
Не поддерживай два независимых описания одного требования. Если область ещё не
перенесена, не создавай в OpenSpec её частичную копию без явного определения границ.
Сейчас перенесённых областей и активных функциональных changes нет.

## Локальный инструмент

Версия CLI закреплена в `tools/openspec/package.json` и `package-lock.json`.
Нужны Node.js версии не ниже 22.12.0 и npm. Для установки из lock-файла:

```sh
npm ci --prefix tools/openspec --ignore-scripts --no-audit --no-fund
```

Запускай CLI через `sh scripts/openspec.sh`. Скрипт отключает телеметрию и
направляет настройки и данные OpenSpec в игнорируемые Git локальные каталоги
`tools/openspec/.config/` и `tools/openspec/.data/`. Он не скачивает зависимости.
Сторонние skills, slash-команды, hooks и глобальные настройки не установлены.
`openspec init` и `openspec update` для текущего workflow не нужны;
не запускай их автоматически: они могут генерировать интеграции для агентов.

## Порядок работы

Пользователь описывает задачу обычным сообщением. Агент читает связанные
контракты и код, проверяет активные changes и создаёт change для согласованного
изменения:

```sh
sh scripts/openspec.sh list
sh scripts/openspec.sh list --specs
sh scripts/openspec.sh new change <имя-изменения>
sh scripts/openspec.sh status --change <имя-изменения>
sh scripts/openspec.sh instructions proposal --change <имя-изменения>
```

Агент готовит `proposal.md`, delta specs, `design.md` и `tasks.md` по схеме
`spec-driven`. Инструкции для остальных артефактов доступны той же командой
`instructions` с именами `specs`, `design` и `tasks`. Существенные изменения
поведения или архитектуры согласуются до реализации; существующее поручение
на конкретную согласованную задачу не требует повторного разрешения.

Для новой области добавь в delta spec содержательный раздел `## Purpose`:
он задаст назначение итоговой спецификации при archive. Иначе CLI создаст
placeholder, который не проходит итоговую проверку `--strict`.

После подготовки артефактов:

```sh
sh scripts/openspec.sh validate <имя-изменения> --strict
```

Агент реализует задачи, запускает проверки проекта из `AGENTS.md`, сопоставляет
результат со сценариями и обновляет затронутую документацию. Формальная проверка
OpenSpec не доказывает соответствие кода требованиям. Незавершённые проверки и
ограничения остаются явными; change не закрывается только по заполненным checkbox.

После выполнения задач и требуемого review агент архивирует change в пределах
поручения и проверяет итоговые спецификации:

```sh
sh scripts/openspec.sh archive <имя-изменения>
sh scripts/openspec.sh validate --all --strict
```

Archive переносит change в архив и применяет delta specs к `openspec/specs/`.
Не обходи проверки archive и не отмечай неподтверждённое поведение реализованным.
Commit и push требуют отдельного явного поручения, как и до подключения OpenSpec.
