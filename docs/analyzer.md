# Контракт Analyzer v0.1

Документ описывает реализованный Analyzer v0.1. Go-контракт не является JSON API или схемой хранения.

## Назначение и границы

Analyzer детерминированно применяет правила к фактам Parser и явно предоставленному пользовательскому контексту. Он не разбирает исходный текст повторно, не обращается к сети, PostgreSQL или Redis, не генерирует постоянные ID или время, не изменяет систему пользователя и не реализует approval.

Четыре правила для записей пакетов создают finding категории `REVIEW`. `UNRESOLVED_BLOCKER` создаёт finding категории `BLOCKER`. Findings по пакетам требуют ручной проверки и не подтверждают опасность обновления; `UNRESOLVED_BLOCKER` сообщает о показанном Portage препятствии. В частности, запланированный downgrade сам по себе не означает ошибку, конфликт или уязвимость. Решение пользователя хранится отдельно и не изменяет finding.

Analyzer может обрабатывать извлечённые записи результата Parser со статусом `partial`. Это не означает, что проверен весь план. Статус и диагностики Parser сохраняются отдельно от findings. Если нет ни записей, ни неразрешённых blockers, список findings пуст. Само отсутствие findings не доказывает безопасность.

## Правила

### `UNRESOLVED_BLOCKER`

Для каждого `Blocker.Resolution = unresolved` создаётся один finding категории `BLOCKER`. Сообщение: «Portage показывает неразрешённую блокировку: <atom>. В представленном плане это ограничение не разрешено.» Тип soft/hard не меняет условие. Разрешённые blockers сохраняются в Parser, findings для них не создаются. Неизвестное состояние не считается подтверждённой блокировкой.

`Finding.EntryIndex` теперь `*int`: для прежних правил содержит индекс с нуля, для blocker — `nil`. `UnresolvedBlockerEvidence.BlockerIndex` указывает на элемент `plan.Blockers`. Нулевой индекс допустим; отсутствие ссылки не кодируется нулём. Новые findings добавляются после прежних findings по пакетам, в исходном порядке `Blockers`. Отдельный порядок правил внутри записи не меняется. Вход только с blockers также анализируется. Статус и диагностики Parser сохраняются; partial не означает, что проверен весь план. Approval не реализуется.

### `DOWNGRADE_PLANNED`

Правило создаёт один finding для каждой записи с `Entry.Operation = downgrade`. Оно опирается на маркер Portage `UD`; Analyzer не сравнивает строки версий и не предполагает причину downgrade.

Если показана ровно одна установленная версия и целевая версия известна, сообщение указывает пару «установленная → целевая» и просит проверить ожидаемость понижения. При отсутствующем или неоднозначном установленном контексте finding сохраняется, но сообщение не выбирает версию и не формирует пару.

`DowngradePlannedEvidence` ссылается на запись плана, её операцию, целевую версию и все показанные установленные версии в исходном порядке. Несколько установленных версий сохраняются как неоднозначный контекст.

**Не срабатывает** для upgrade и `NS` / install.

### `LOCAL_PATCHED_PACKAGE`

Правило применяется к каждой записи плана, если её точная пара `category/name` присутствует в явно предоставленном пользователем списке локально патченных пакетов. Контекст задаётся точными `category/name`: wildcard, ограничения версий и SLOT-селекторы не поддерживаются. Повтор одного имени в списке контекста не создаёт дубликатов findings.

Evidence содержит запись плана и конкретное пользовательское указание о локальных патчах. Сообщение просит проверить применимость патчей и не утверждает, что патчи сломаются. Analyzer не определяет наличие патчей по имени пакета, в том числе по имени пакета ядра.

**Не срабатывает**, если точного совпадения `category/name` нет. Совпадение проверяется отдельно для каждой записи плана; поэтому несколько совпавших записей дают по одному finding на запись.

### `USE_CHANGED`

Правило срабатывает, если в группе с точным именем `USE` есть хотя бы один токен, в нормализованных `Markers` которого присутствует `*` или `%`. Analyzer использует структурированные факты Parser и не ищет эти символы повторным разбором `RawToken` или исходной строки.

Для одной записи все затронутые токены объединяются в один finding в исходном порядке. Токен с обоими маркерами включается один раз. Evidence содержит исходную запись и конкретные токены группы `USE`.

Сообщение описывает показанные Portage изменения. Оно не приписывает им причины и не обещает полный diff конфигурации. Изменения только в `PYTHON_TARGETS`, `L10N` и других группах этим правилом пока не интерпретируются. Скобки и `-` без `*` или `%` сами по себе не запускают правило. Маркер `~` пакета не является USE-изменением.

**Не срабатывает**, если в группе `USE` нет токенов с `*` или `%`, в том числе когда такие маркеры есть только в другой группе.

### `SLOT_CHANGED`

Правило срабатывает только при одновременном выполнении всех условий:

- `Operation = upgrade` или `downgrade`;
- `InstalledContext` содержит ровно одну показанную установленную версию;
- установленный и целевой `SLOT` явно известны;
- значения SLOT различаются.

Evidence содержит запись с обоими показанными SLOT. Правило сравнивает SLOT, а не SUBSLOT.

**Не срабатывает** при `NS` / `install` в новый SLOT, изменении только SUBSLOT, неизвестном SLOT или нескольких показанных установленных версиях. Если установленных версий несколько, Analyzer не выбирает одну для сравнения.

## Результат и порядок

Точка входа — `analyzer.Analyze(plan parser.Result, context analyzer.Context) analyzer.Result`. Функция детерминирована и не выполняет I/O, сетевые запросы, повторный разбор текста, генерацию постоянных ID или времени, а также не изменяет входные структуры.

`Context` содержит упорядоченный список точных `parser.Package` в `LocallyPatchedPackages`. Сравниваются только `Category` и `Name`; wildcard, ограничения версий и SLOT-селекторы не интерпретируются. Если совпадают повторяющиеся элементы, evidence ссылается на первый.

`Result` содержит исходные `parser.Status` и `parser.Diagnostic` в прежнем порядке, а также список `Finding`. Копии диагностик сохраняют их поля и порядок; `SourceLines` остаются нумерованными с единицы. Пустой список findings не означает успешный разбор или безопасность плана.

Каждый `Finding` содержит `RuleID`, `Category`, `Message`, `EntryIndex` и типизированный `Evidence`. `EntryIndex` — необязательный индекс с нуля в `plan.Entries`; для blocker он отсутствует. `RuleID` принимает `DOWNGRADE_PLANNED`, `LOCAL_PATCHED_PACKAGE`, `USE_CHANGED`, `SLOT_CHANGED` или `UNRESOLVED_BLOCKER`. Категория последнего — `BLOCKER`, остальных — `REVIEW`.

Виды evidence различаются типами Go:

- `LocalPatchedPackageEvidence.ContextIndex` указывает на первый совпавший элемент `Context.LocallyPatchedPackages`.
- `UseChangedEvidence.Tokens` содержит ссылки `UseTokenRef` на индексы группы `FlagGroups` и значения `Values`; оба индекса начинаются с нуля.
- `SlotChangedEvidence.InstalledVersionIndex` указывает на единственную установленную версию. Целевой SLOT находится в `Target.Slot` той же записи Parser, на которую указывает `EntryIndex`.
- `DowngradePlannedEvidence` указывает на индекс записи, показанную операцию и версии без выбора между несколькими установленными версиями.

Отсутствующие ссылки не кодируются индексом `0`: индекс `0` — допустимая ссылка. Evidence не сериализуется и не преобразуется в сохраняемые сущности на этом этапе. Постоянные ID и преобразование результата для backend относятся к будущей работе.

На каждую пару «правило и запись пакета» создаётся не более одного finding; одна запись может иметь несколько findings. Записи обрабатываются в исходном порядке Parser. Правила внутри записи идут в таком порядке:

1. `DOWNGRADE_PLANNED`;
2. `LOCAL_PATCHED_PACKAGE`;
3. `USE_CHANGED`;
4. `SLOT_CHANGED`.

Для upgrade и `NS` правило `DOWNGRADE_PLANNED` не создаёт finding, поэтому прежний относительный порядок остальных правил сохраняется.

Повтор пакета в пользовательском списке контекста не меняет порядок и количество findings.

## Примеры и ожидаемое поведение

### Существующий fixture

Реальный пример — [testdata/parser/ebuild-updates.txt](../testdata/parser/ebuild-updates.txt) и его фактическое описание [testdata/parser/ebuild-updates.expected.md](../testdata/parser/ebuild-updates.expected.md). Для этого fixture без пользовательского контекста ожидается ноль findings:

- в группе `USE` нет маркеров изменения `*` или `%`;
- `sys-kernel/gentoo-kernel-bin` устанавливается через `NS` в новый SLOT;
- `virtual/dist-kernel` сохраняет SLOT `0`, меняя только SUBSLOT.

Это результат применения описанных правил к перечисленным фактам Parser. Он не доказывает безопасность плана.

### Условные примеры

Примеры ниже иллюстрируют контракт и не являются реальными выводами Portage.

- **Локальные патчи:** если запись `dev-libs/example` совпадает с точным элементом пользовательского списка, создаётся `LOCAL_PATCHED_PACKAGE`. Если совпадения нет, finding не создаётся. Два одинаковых элемента `dev-libs/example` в списке всё равно дают один finding на каждую запись плана. Если в плане две записи с этим именем, создаются два findings — по одному на запись.
- **USE:** если у одной записи два токена группы `USE` содержат `*` или `%`, один `USE_CHANGED` finding перечисляет оба токена в исходном порядке. Токен с `*` и `%` включается один раз. Маркеры только в `PYTHON_TARGETS` не запускают правило.
- **SLOT:** при `upgrade`, одной установленной версии и явно показанных разных SLOT создаётся `SLOT_CHANGED`. Разные SUBSLOT при одинаковом SLOT не запускают правило. Правило также не срабатывает, если любой SLOT неизвестен или показаны несколько установленных версий.
- **Downgrade:** `UD` создаёт `DOWNGRADE_PLANNED` категории `REVIEW`; при одной установленной версии сообщение показывает направление от установленной версии к целевой. Из нескольких версий Analyzer не выбирает одну. Реальных downgrade fixtures пока нет, это поведение проверяется синтетическими строками.
- **Несколько правил:** если одна запись одновременно совпадает с локальным контекстом, содержит USE-маркеры `*` / `%` и удовлетворяет условию SLOT, она получает три findings в установленном порядке правил.
- **Partial:** при статусе Parser `partial` Analyzer оценивает извлечённые записи и не объявляет весь план проверенным. Статус и диагностики Parser остаются отдельными от findings.
- **Нет записей:** findings по пакетам отсутствуют; неразрешённые blockers по-прежнему создают findings. Это не является доказательством безопасности.

## За пределами v0.1

В этой версии не реализуются `BLOCKER_PRESENT`, `DEPENDENCY_CHANGED`, security findings, анализ upstream и metadata, review acknowledgements и approval. Новые правила требуют отдельного согласования.

## Реализация и проверки

Реализация находится в `internal/analyzer`; тесты вызывают `Analyze` на реальном Parser fixture и типизированных синтетических фактах Parser. Реальных downgrade fixtures пока нет. Проверки проекта: `gofmt` для изменённых Go-файлов, `go test -count=1 ./...`, `go vet ./...` и `git diff --check`.
