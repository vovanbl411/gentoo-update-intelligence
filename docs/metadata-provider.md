# Локальный Metadata Provider

Документ задаёт контракт первого локального Metadata Provider. Реализации пока нет. Provider читает точный cache-файл из объектов одного закреплённого commit подготовленного локального Git-репозитория и передаёт его существующей `metadatadiff.Normalize`.

## Назначение и границы

Один Provider обслуживает один логический repository и один commit. Реестр нескольких Provider не нужен. Provider не подключён к `ChangeReport` или `Analyzer` и не определяет операцию плана или не собирает отчёт.

Provider использует локальный репозиторий как подготовленный источник и читает содержимое из Git-объектов указанного commit. Текущая ветка, выбранный checkout, изменения рабочего дерева и untracked-файлы не влияют на результат.

Provider не выполняет clone, fetch, pull, checkout, сетевые запросы, ebuild или генерацию metadata. Он не изменяет Git-репозиторий, не ищет историю автоматически и не подбирает fallback-источник, другую версию или ревизию.

## Go API

Планируемые точки входа:

```go
func Open(config Config) (*Provider, error)
func (p *Provider) Lookup(query Query) (LookupResult, error)
```

`Config` — доверенная настройка приложения:

- `Repository` — логическое имя repository;
- `SourceURL` — заявленный адрес источника для provenance;
- `LocalPath` — путь к подготовленному Git-репозиторию;
- `Commit` — полный commit SHA.

`Open` проверяет доступность локального Git-репозитория и наличие заданного commit. Ветка, tag или сокращённый SHA не заменяют полный SHA. Нельзя навязывать длину SHA без учёта формата объектов репозитория. `SourceURL` не проверяется по сети: это заявленное происхождение, а не доказательство того, что локальный репозиторий получен именно по этому адресу.

`Query` содержит `Repository`, `Category`, `Name` и `Version`. Запрос не может переопределить `LocalPath`, `SourceURL` или `Commit`.

Концептуальные статусы `LookupResult`:

- `found` — точный cache-файл прочитан, а `Snapshot` получен через существующую `Normalize`;
- `not_found` — точного cache-файла нет в закреплённом commit;
- `repository_unavailable` — запрошенное имя repository не совпадает с настройкой Provider.

`Snapshot` присутствует только при `found`. Если найден обычный cache-файл с повреждённым содержимым, результат всё равно `found`: `Snapshot` содержит исходные данные и диагностики `Normalize`. Это не `not_found` и не ошибка чтения.

## Путь и проверка запроса

Provider строит путь из проверенных компонентов запроса:

```text
metadata/md5-cache/<category>/<name>-<version>
```

Нельзя принимать путь cache целиком от вызывающего кода. `Category`, `Name` и `Version` валидируются по синтаксису Gentoo. Проверка запрещает абсолютные пути, `/` в компонентах, `..` и управляющие символы, не запрещая корректные имена, ревизии `-rN` и суффиксы версий Gentoo. Точные правила проверки должны соответствовать грамматике Gentoo и быть закреплены тестами реализации.

Некорректный запрос возвращает распознаваемую ошибку валидации. Точный порядок обработки запроса, который одновременно некорректен и содержит несовпадающий `Repository`, остаётся открытым до реализации.

## Работа с Git и ошибки

Чтение выполняется только из commit, заданного при `Open`. Пользовательские значения не должны становиться опциями Git или произвольными revision expressions. Вызовы Git, если они потребуются, выполняются без shell и с отдельными аргументами. Контракт фиксирует обязательное поведение, но пока не выбирает конкретные команды или внутренний алгоритм.

Provider проверяет тип записи дерева до чтения содержимого. Обычный cache-файл читается как файл из Git-объекта. Если по ожидаемому пути находится symlink, каталог, submodule или иной неподдерживаемый объект, Provider возвращает явную ошибку и не разыменовывает объект, не трактует его как обычный файл.

Результаты ошибок различаются:

- некорректная конфигурация или отсутствующий/неприемлемый commit приводят к ошибке `Open`;
- некорректный запрос приводит к распознаваемой ошибке валидации `Lookup`;
- невозможность прочитать Git-объекты приводит к ошибке чтения;
- отсутствие записи по точному пути в дереве commit даёт `not_found`.

Нельзя классифицировать любую ошибку Git как `not_found`: отсутствие записи дерева и неисправность чтения — разные результаты. Окончательные Go-типы ошибок и их коды остаются открытыми до реализации.

## Snapshot и provenance

При `found` Provider формирует `metadatadiff.Source` из проверенного запроса и настроек:

| Поле `Source` | Значение |
|---|---|
| `Category`, `Name`, `Version` | Проверенные значения запроса |
| `Repository` | Логическое имя из конфигурации Provider |
| `SourceURL` | Заявленный адрес из конфигурации Provider |
| `Commit` | Фактически выбранный полный commit |
| `CachePath` | Точный путь объекта cache в commit |

Содержимое cache передаётся в `metadatadiff.Normalize` без изменений. `Normalize` сохраняет `Content` и вычисляет SHA-256 его точного содержимого. Git blob SHA и SHA-256 содержимого — разные значения и не должны смешиваться.

`not_found` означает только отсутствие точного cache-файла в выбранном commit. Он не доказывает, что пакет никогда не существовал. Provider не ищет автоматически другую версию или ревизию. Снимки `before` и `after` запрашиваются отдельно. Наличие снимка не доказывает, что эти metadata соответствуют установленной сборке.

## План проверок реализации

Будущие тесты используют небольшой временный Git-репозиторий без сети и клонирования Gentoo. Локальные `git init`, `git add` и `git commit` допустимы только для подготовки тестовых данных. Сам Provider не изменяет репозиторий.

Тесты должны проверить:

- чтение обычного cache-файла, точное сохранение содержимого и provenance, SHA-256 через `Normalize`;
- отсутствие точного файла и неподдерживаемый `Repository`;
- некорректные запросы и попытки выйти из заданного пути;
- ошибку `Open` для отсутствующего или некорректного commit;
- чтение закреплённого commit при другой текущей ветке;
- независимость результата от локальных изменений и untracked-файлов;
- отказ читать как cache-файл symlink, каталог и submodule;
- статус `found` и диагностики `Normalize` для повреждённых metadata;
- различение отсутствующей записи дерева и ошибки чтения;
- отсутствие изменений в рабочем дереве и Git refs после вызовов Provider;
- повторяемость чтения.
